## 既存仕様書との乖離・注意点

既存の `other.md`
には、メールアドレス一致による紐付けを避ける記述、ログインモーダル、追加情報入力ステップの想定があります。現行実装は`/auth/signin`
ページの Google OAuth のみで、NextAuth callback 内で `User` と `Account`を即時作成または更新します。同一 email の既存
`User` がある場合は、新しい OAuth `Account` をその `User` に紐付けます。

## 実装場所

- `src/library-setting/auth.ts`
- `src/app/api/[...nextauth]/route.ts`
- `src/app/auth/signin/page.tsx`
- `src/components/auth/sign-in-button.tsx`
- `src/middleware.ts`

## 認証方式

- NextAuth v5 beta を利用します。
- Provider は Google のみです。
- session strategy は JWT です。
- session maxAge は30日、updateAge は24時間です。
- sign-in page は `/auth/signin` です。

## サインイン画面

`/auth/signin` は Googleログインボタンを表示します。ボタンは`signIn("google", { callbackUrl: "/dashboard/group-list" })`
を呼びます。画面自体に追加情報入力フォームはありません。

## SignIn callback

Google OAuth callback では次の順序で DB を同期します。

1. `email`, `account`, `providerAccountId` が欠けている場合は sign-in を拒否します。
2. Prisma transaction を開始します。
3. `provider + providerAccountId` で既存 `Account` を検索します。
4. 既存 `Account` がある場合は、OAuth token fields と対応する `User` の email/name/image を更新します。
5. 既存 `Account` がなく、同じ email の `User` がある場合は、その `User` に新しい `Account` を作成します。
6. 同じ email の `User` もない場合は、新しい `User` と `Account` を作成します。

## JWT callback

- 初回 sign-in 時は `Account` から DB上の `User` を取得し、`token.id`, `token.email`, `token.name`, `token.image`
  に反映します。
- `Account` からユーザーを特定できない場合、email fallback で `User` を探します。
- `account.access_token` があれば `token.accessToken` に保存します。

## Session callback

- `token.id` を `session.user.id` に反映します。
- email/name/image も token から session に反映します。
- `session.expires` を設定します。

## Middleware

`src/middleware.ts` は `/dashboard/:path*` のみを保護します。

- 未認証の場合は `/auth/signin?callbackUrl=<元pathname>` に redirect します。
- 認証済み response には以下のヘッダーを付与します。
  - `X-Frame-Options: DENY`
  - `X-Content-Type-Options: nosniff`
  - `Strict-Transport-Security: max-age=31536000; includeSubDomains`
  - `Referrer-Policy: strict-origin-when-cross-origin`
- middleware error 時は `/error` に redirect します。

## 共通ヘルパー

- `getAuthSession()`
  - NextAuth session を取得します。
- `getAuthenticatedSessionUserId()`
  - 認証済みユーザーIDを返します。
  - 未認証時は `/auth/signin` へ redirect します。

## 認証が必要な主な画面

middleware により `/dashboard` 配下全体が保護されます。Server Action 側でも、更新系の多くは `getAuthSession()` や
`getAuthenticatedSessionUserId()` を使って認証ユーザーを取得します。

## 注意点

- `/dashboard` 以外の API
  Route は middleware では保護されません。APIごとに認証チェックを持つものと、持たないものがあります。
- 設定更新の一部 action は `userId` を引数で受け取り、action 内で session
  user と一致するかまでは確認していない箇所があります。
- テスト側には旧 import path や matcher 期待値が残っている箇所があります。この文書は現行実装を優先します。
- 旧要求メモには「メールアドレス一致で同一ユーザー扱いしない」方針がありました。現行実装は
  `provider + providerAccountId` を最優先にしつつ、未登録 OAuth account では同一 email の `User` に新しい `Account`
  を紐付けます。

## v0.1：ログイン

1. 「アプリを利用する」ボタンを押して、ログイン画面のモーダルを表示
   - 「新規登録 / ログイン」の流れ
     1. 「アプリを利用する」Buttonを押す
     2. ログインするモーダルを表示
     3. Googleアカウントにログインして認証する。
        - Googleアカウントのログインのみ用意
        - ユーザーIDを参照してログインする
     4. ログイン後に、ログイン成功の場合は無料主義アプリ内に遷移する
   - ポイント
     1. **ログイン用ボタンと新規登録用ボタンは分けない**（同じ「アプリを利用する」等の導線から開く**同一モーダル**内で、新規登録用とログイン用の**別ボタンを置かない**）
2. 一致条件
   - 参考
     - [https://qiita.com/ritou/items/00990e00151fad46df1a](https://qiita.com/ritou/items/00990e00151fad46df1a)
   - 要件
     1. 「アプリ内で保存しているGoogleのユーザーID」と「ログイン処理の戻り値のGoogleのユーザーID」で一致したらログインできる仕様にする。
     2. メアドで一致はNG！
   - ポイント
     1. 「パスワード」と「メアド or 電話番号など」では、新規登録/ログインは別である必要がある
        - 「パスワードの登録」と「パスワードの検証」の違いの為
   - メアド一致でログインがNGな理由
     1. 「Google内の設定メアド」と「無料主義アプリ内の設定メアド」のどちらも、後から変わることがあるため。
     2. メアドのリサイクル後、そのメアドは別人のメアドになっていることもあるため。
   - ベストな仕様
     1. 新規登録
        - Google認証後、Google認証で取得できないデータを入力する新規登録画面で情報入力して、Google認証で返ってきたGoogleのユーザーidと無料主義アプリ内のユーザーidを紐づけて保存
     2. ログイン時
        - 「Google認証から受け取ったユーザーID」と「自サービスに保存しているGoogleのユーザーID」が一致した場合にログイン
     3. 無料主義アプリ内で追加で別SNS連携機能を追加する場合
        - ログイン中のユーザーIDと紐づけて、その別のSNSのユーザーIDを保存する。
        - アプリ内で追加で別SNS連携機能を追加する機能を作る理由は、その別のSNS認証でログインしても、そのアカウントに入ることができるため。
          - その機能がないと、Xで最初新規登録した場合、Metaで再度ログインするとアカウントが新規作成される。なので、Xでログイン中にMetaアカウントも、アプリ内アカウントに連携させることで、ログアウト後にMetaアカウントからも同じアカウントとしてログインできるようになる。
          - アプリ内で追加で別SNS連携機能を追加する機能のために、MetaとXのユーザーIDは、それぞれが無料主義アプリ内ユーザーIDと紐づけて保存する必要がある。- 具体的には、ユーザーIDだけでなく、"IdPの識別子 +
            IdPから受け取ったユーザー識別子" を利用しよう
            - 例）IdPの識別子は、Google、Meta、Tiktokなのか、などのサービスの識別子
              - IdPから受け取ったユーザー識別子は、ユーザーIDのこと
   1. 横着な設計の例
      1. NG実装例の「メアド一致」でログインさせるサービスに多いのが、パスワード認証やメールでリンクを送信して認証させる仕組みを実装してから、後でSNS認証を追加実装した場合。
         - その場合は、 ユーザーがメール認証などで利用しているので、後からアプリ内で別のログイン方法としてSNS連携もしてね！と言ってもしてくれないし、 セッションが切れてログアウトして、再度ログインするときに、SNS認証してきた時に、前回はメアド認証でメアドだけDBに保存されていて、SNS認証のメアドをも取得できた。
         - その時に、追加でメアド認証時のパスワードを再度入れてもらって、SNSのユーザーIDも紐づける対応をすれば良いけど、その部分の実装が面倒だから、SNS認証時のメアドが前回のメアド認証のメアドと一致したらログインできる仕様にしてしまっている。
         - 本当は、前回のメアド認証のメアドとSNS認証のメアドが一致したら、前回のメアド認証のアカウントを見せて、このアカウントですか？と伝えて、追加でメアド認証時のパスワード入力を求めたりして、パスワードが合っていたら、SNS認証のユーザーIDとメアド認証のアプリ内ユーザーIDを紐付けてDBに保存して、前回のアカウントにログインできるようにすべき。
         - その「前回のメアド認証のアカウントを見せて確認するフェーズ」をすっ飛ばしてメアド一致でログインさせちゃうのがNG
           - 3の場合、本当はアカウントがある可能性があるのに、新規で作成するのは、ユーザーに面倒をかけるので、できれば避けたい。セキュリティ的には大丈夫だが。
           - 内部でユーザーに紐づくメールアドレスがユニークになってる場合は、別のメールアドレスを登録させる必要が出てくるので、ここでもユーザーに面倒をかける。
           - 「すでに使用されたメアドです。」と表示されてしまう問題が起きる。
           - 正解の設計は、2。既存ユーザーの認証をパスワードなどで行なった上で、SNS認証のユーザーIDとアプリ内のメアドとアプリ内ユーザーIDの紐付けを行う実装をお勧めします。
   2. オススメの追加機能
      - 新規登録時に使用したSNS認証とは別のSNSで認証したい場合は、新規登録後にアプリ内アカウント設定画面から、ログインで使用したいSNSでも連携(認証)を事前にできるようにする。
      - その際にも、ログイン時にメアドではなく、ユーザーIDが一致したかで判定する必要がある
   3. オススメの設計
      1. Googleから受け取ったユーザーIDとサービスのユーザーIDの紐付けてDBに保存して、「Googleアカウントでログイン」ではそれを見る
      2. アプリ内のメアドとして使う分には、Google認証のGoogleメアドを使うことは大丈夫。
         - だが、ログイン時にメアド参照することがNG
         - そのGoogle認証時のメアドにお知らせを送る。とかは別にOK
      3. 再度のログイン時に、「Googleから受け取ったメアド」と「アプリに設定済みのメアド」が違ったら、Googleから受け取ったメールアドレスで上書きするか？とユーザーに聞いた方が親切
      4. Google アカウントのメールアドレスは変更される可能性があるため、ユーザーの識別には使用しない
      5. 代わりに、クライアントで
         `getBasicProfile().getId()`を使用して取得できるアカウントの ID を使用し、バックエンドで ID トークンの
         `sub`クレームから取得
   4. メアドで一致したらログインがNGの具体的な事例
      - アプリ内に設定したメアドが変わるかもだし、Googleに設定したメアドが変わるかも
      1. アプリ内に設定したメアドが変わる場合
         - アプリは基本Google認証したらGoogle認証したメアドをDBに保存してアプリ内メアドとしても、そのメアドを設定する。
         - だけど、メアドを変えたいからアプリ設定でメアドを変更しても、Googleの設定メアドは同期されて変更されることはない。
         - つまり、↑の変更では、アプリ設定メアドはBだけ変更され、Google設定メアドはそのまま
         - なので、アプリ設定メアドを変更後にログインする場合、再度Google認証する時に、メアドをキーで参照してログインできるようにしていると、アプリ設定メアドはBだけど、GoogleメアドはAなので、認証失敗＆「すでにアプリで使用されています」と表示されてしまう。
         - なので、ログインはユーザーIDで行う必要がある。
   5. Googleに設定したメアドが変わる場合
      - Googleに設定したメアドが変わる場合は、元のメアドは利用不可能となる設計になっている。
      - そのため、元のメアドをDBに保存して、メアド参照でログインしているアプリには、Googleのメアド変更後に、元のメアドで入ろうとしても、メアドが廃止しているため入れないし、変更後のメアドではなく、元のメアドを使わないとアプリに入れないのも設計としておかしい。
      - なので、Googleから受け取ったユーザーIDをキーにしてサービス内のユーザーを参照する必要がある。
3. アカウントが無い場合の対応
   - 説明
     - Google 認証の結果、DB 上に紐づくアプリ内アカウントが無い場合は、**上記 1. と同じモーダル**のまま、新規登録に必要な追加情報の入力（プロフィール等）のステップへ進ませる。**「新規登録専用ボタン」で別画面へ遷移する**ような分岐にはしない（ログイン用／新規登録用のボタン分離は行わない）。
     - 既に紐づいているアプリ内アカウントがあれば、そのままアプリ内へ遷移する。
4. メアド登録時のエラーバリデーションについて
   - 参考
     - [https://qiita.com/ritou/items/00990e00151fad46df1a](https://qiita.com/ritou/items/00990e00151fad46df1a)
   - 説明
     1. メアドはユニークにする
        - アプリ内DBでメアドはユニークにする制約を設定することが大半
     2. メアドの重複登録防止の表示方法
        - メアドの重複登録防止のために、重複したメアド入力時に「既に使用されています」を表示する機能があると攻撃者がサービス内で、このメアドが使用されていることを認識できてしまう。**なので、使用されていることを表示してはダメ**
          - そのため重複したメアド・パスワードが入力されたら「メアドもしくはパスワードが正しくありません。」とかのエラーを返して「どうしてもログインできないときは」みたいなリカバリーフローに流す方法を提案が良い
