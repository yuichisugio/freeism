# Accounts v0.1 実装計画

## 実装の入力

[v0.1仕様](../specification/v0.1/main.md)の確定事項と受け入れ条件に従って、下記の移管・接続作業を行う。
仕様の未決事項を実装前に確認し、各フェーズで必要な項目を確定する。
移行準備時に、下記モジュールの実装状態、各環境のデプロイ状況、保存済みデータの有無を確認する。

## 実装順序

### 1. 接続契約と移行対象を確定する

- [仕様の未決事項](../specification/v0.1/main.md#未決事項)を整理し、API契約を確定する。
- 要件定義がすべて確定した後に、Accountsのテーブル構造・一意制約・関連・索引を設計する。設計結果からmigrationとテストの作成へ進む。
- 表の移行元から呼出元を追い、認証フック、CSV照合、未受領分の受領、プロフィール表示、アカウント閉鎖・再開、定期処理まで移行対象を確定する。
- ソースコードの移管と保存済みデータの移行を分け、各環境のデータ有無・稼働状態に応じて切り替え手順を定める。

### 2. Accountsの仕様からテストを作成する

- [受け入れ条件](../specification/v0.1/main.md#受け入れ条件)を各テストケースへ対応付ける。
- 移行元のURL正規化・リンク抽出・安全取得のテストを棚卸しし、Accounts側のテストへ移管する。
- 単体テストと、認証・DB・APIの境界を確認する結合テストを分ける。実装前に期待した失敗を確認する。

### 3. Accountsへ機能を移管する

- 外部認証・紐付け、共通のWebページ取得・リンク検証、公開プロフィール、公開設定、照合APIを仕様に従って実装する。
- JSON入出力と復元・移行の処理を実装し、[バックアップと移行の仕様](../specification/v0.1/main.md#jsonによるバックアップと移行)に対応するテストを実行する。
- 所有権証明を受領・ポイント計上処理から分離し、Accountsが担当する画面・API・保存処理を揃える。
- [外部識別情報の仕様](../specification/v0.1/main.md#外部識別情報の仕様)と[Webページの検証仕様](../specification/v0.1/main.md#webページの検証仕様)に対応する実装差分を確認する。
- 対応する単体・結合テスト、型検査、静的検査を実行する。

### 4. Pointsの利用側を切り替える

- CSV検証・確定、未受領分の受領、プロフィール、アカウント閉鎖・再開など、外部アカウントに依存する処理を確定したAccounts API契約へ接続する。
- PointsのCSVで指定する識別子の形式を確定し、URL・外部サービス名と固有ID・AccountsユーザーIDをAccounts APIへ渡す入力処理と確認画面を実装する。
- Points側の外部アカウント管理の導線をAccountsへ向ける。
- Accountsの一覧取得APIをPointsのプロフィール・公開APIへ接続し、提供を許可した外部アカウントの表示を確認する。
- [サービス間の境界](../specification/v0.1/main.md#pointsなどの連携サービスとの境界)に従い、独立した認証と情報連携を結合テストで検証する。
- Pointsの未受領分・確定済み貢献に関する回帰テストを実行する。

### 5. 移管を完了する

- Accountsでの機能提供とPointsからの利用を確認し、Points内の移管済み処理・画面・APIを整理する。
- 移管元の所有権管理に付随する処理・Cron・監視・DB定義の呼出関係を確認し、仕様に定めた現在の紐付け管理とPointsの経済履歴に合わせて整理する。
- 両アプリの仕様・実装計画・テスト・設定手順を、切り替え後の責務に合わせて更新する。

## 検証の実行と完了確認

- 各フェーズで単体テスト、結合テスト、型検査、静的検査の結果を記録する。実行コマンドは実装時点の各アプリのpackage scriptsを確認して選ぶ。
- [受け入れ条件](../specification/v0.1/main.md#受け入れ条件)とテスト結果を突き合わせ、未検証項目を確認する。
- 移行元モジュールの呼出元を再検索し、Points側の参照・設定・監視の整理漏れを確認する。
- 変更したMarkdownの相対リンクと仕様参照を検査し、実装差分と文書を独立レビューする。
