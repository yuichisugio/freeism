# Accounts v0.1 実装計画

## 実装の入力と進め方

[Accounts v0.1仕様](../specification/v0.1/main.ja.md)と[URL検証仕様](../specification/v0.1/verify-url.ja.md)の確定事項・受け入れ条件を入力とし、以下の実装・移管・検証を進める。
要件と振る舞いは仕様書に集約し、この文書では作業順序、導入手順、確認方法を管理する。
未決事項は対応する実装に着手する前に確定し、テーブル構造を更新してからmigrationを作成する。
既存コードは移管対象を調べる資料として扱い、採用する構成は現行仕様と標準機能から決める。
実装の構造や細部は、利用者の目的と保守性を満たす、より良い方法を柔軟に選ぶ。サブエージェントには成果物と担当範囲を渡し、調査・実行の進め方は担当へ任せる。
Sol 6のサブエージェントは調査、文書記載、実装、レビュー、PR更新を担当する。Astra 6のメインエージェントは全体を管理し、レビュー結果と実装差分を敵対的にレビューする。指摘は現実的な利用フローでトリアージし、修正要否を判断する。
この要件定義の対話中は、回答を仕様書へ反映してレビューを省略する。実装・PRなどのレビュー方針は、その作業時に適用する。
認証の追加拡張が必要になった場合は、標準機能で満たせない理由と追加案を整理し、ユーザーの承認後に実装する。

- v0.1の実装は専用の`codex/`ブランチで進め、PRを作成し、そのPRのブランチへ実装・テスト・文書の変更をpushする。
- 初期の実装差分をdraft PRとして共有し、以後のpushで更新する。PRに仕様参照、検証結果、Preview URLを記載する。
- フェーズごとに最小の動作単位を実装・検証する。ユーザーの権限、所有者の一意性、保存結果に必要なチェックをバックエンドに置く。
- Pointsとの接続変更は[Points実装計画](../../../points-web-app/plan/v0.2-implementation.md)と連携する。

## 1. 開発基盤と構成を整える

- Valibot、Hono、Drizzle、Better Auth、TanStack Start、React、HeroUI v3、Tailwind CSS、Vite Plus、linkify-itを導入する。依存関係は既存のpnpm運用で管理し、必要に応じて適切な版へ更新する。
- [提供・技術要件](../specification/v0.1/main.ja.md#提供技術要件)に従い、HonoのHTTP境界、機能ごとの処理、DrizzleによるDBアクセスを分ける。外部接続の差し替えとテストに必要な境界に絞ってクリーンアーキテクチャを適用する。
- フロントエンドは機能単位のディレクトリにビューとフックを分ける。API呼出し、状態管理、保存・検証操作を機能ごとのフックに集約し、ビューは受け取った状態と操作を描画へ結び付ける。
- 入出力のValibotスキーマを共通モジュールへ置き、画面入力とHonoの入力境界の両方で同じ検証を実行する。セッションの本人確認とDB上の権限確認はバックエンドで行う。
- TypeScriptの`strict`を有効にし、Better Authの`$Infer`とHonoのルート型から型を取得する。
- Hono 4.13.0以降の`app.query()`を使い、APIのPATHとハンドラーを同じ宣言にまとめる。機能別のルートファイルは`app.route()`で接続し、型推論を保つ。[Honoの構成ガイド](https://hono.dev/docs/guides/best-practices)を参照する。
- [Cloudflare Vite PluginとTanStack Startの公式構成](https://developers.cloudflare.com/workers/framework-guides/web-apps/tanstack-start/)を接続する。TanStack Startの事前生成（`prerender`）で、AccountsユーザーIDの無い経路（`/`・`/help`など。`vite.config.ts`の`pages`）を生成し、画面の生成物をassetsへ接続する。ID付きの経路（`/{accountsUserId}/...`）はassetsに無いため、Workerのfallbackで同じshellを返す。`src/frontend/start.ts`の`createStart`で`defaultSsr: false`とし、`__root.tsx`の`ssr`でトップページ（`/`）だけ内容を含めて生成する。ほかの画面は中身の無いshell（`help.html`など）として出力し、ブラウザーで最初から描画する。`src/index.ts`のHonoはAPI・認証・公開プロフィールのSSRを担当し、Vite Plus経由の開発・ビルド・プレビューを整える。

## 2. Workersの実行・配信・運用環境を整える

### WranglerとBindings

- `wrangler`をアプリの`devDependencies`へ追加する。Worker Previewsに必要な版を満たす最新版を選び、プロジェクト内のCLIで実行する。
- `wrangler.jsonc`に`main: "src/index.ts"`、`upload_source_maps: true`を設定する。Cloudflare Vite Pluginは`wrangler.jsonc`の`minify`を使わないため、Workerの圧縮とソースマップ出力は`vite.config.ts`の`environments.ssr.build`の`minify: true`・`sourcemap: true`で設定する。
- `compatibility_date`を導入時の最新日付にし、`compatibility_flags: ["nodejs_compat", "global_fetch_strictly_public"]`を指定する。日付・flagを更新した差分でビルドとWorkers上のテストを実行する。
- `placement: { mode: "smart" }`を設定し、D1アクセスと公開画面の応答時間を確認する。静的アセットをWorker経由にした場合の配置の影響も計測する。
- 本番・stagingの変数、D1、Secret、認証callbackを環境別に設定し、Preview用の`previews`設定を整える。
- `pnpm exec wrangler types --env-interface CloudflareBindings`で`worker-configuration.d.ts`を生成し、`tsconfig.json`の`compilerOptions.types`へ接続する。環境設定の更新後も型を再生成する。
- 型検査scriptを`pnpm exec wrangler types --env-interface CloudflareBindings && tsc --noEmit`として登録する。
- デプロイ先の秘密値は`pnpm exec wrangler secret put`で登録する。ローカルではgit管理外の`.env.local`またはシェル環境から読み込み、必要な変数名と説明を`.env.example`へ記載する。[環境変数の公式手順](https://developers.cloudflare.com/workers/local-development/environment-variables/)に従って、選択した環境での読み込みを確認する。

### 静的ファイル・公開HTML・キャッシュ

- JS、CSS、画像、事前生成した画面をWorkersの`assets`へ接続する。出力先はCloudflare Vite Pluginが生成する配信設定と揃える。
- API、OAuth関連endpoint、`/.well-known/*`をWorkerで処理する。`/api/*`・`/.well-known/*`の未定義のパスは、Honoアプリで404のProblem Detailsを返す。`/profiles/*`は公開プロフィール専用エントリーポイントへ渡し、キャッシュミス時にHonoがD1から在籍ユーザーの表示名・固定IDと一般公開を許可された外部アカウント情報を読み、HTMLをSSRして`c.html()`で返す。公開する外部リンクが0件でもプロフィールを返し、退会などでユーザーが存在しない場合とban中のユーザーは404を返す。[HonoのHTML応答](https://hono.dev/docs/api/context#html)、[Workers Cache](https://developers.cloudflare.com/workers/cache/)を参照する。
- 表示名・外部アカウントの一般公開設定の変更、外部アカウントの解除・所有者の変更・退会・ban・unbanなど、プロフィールの表示内容に影響するDB更新後、影響するプロフィールのWorkers Cacheを`ctx.cache.purge({ pathPrefixes: ["/profiles/{accountsUserId}"] })`でpurgeする。所有者の変更では旧・新双方のプロフィールを1回の呼出しで対象にする。次の取得でD1からユーザーの存在と公開対象を読み直してHTMLまたは404を返す。テンプレート変更時もキャッシュをpurgeする。Workers Cacheのpurgeは契約プランによらずFree枠の頻度制限（アカウント単位で1分5要求、bucket 25）を受けるため、公開内容が変わる更新だけを対象にする。結果の`success`が`false`の場合は`errors`をログに残し、edgeのTTLで収束させる。操作した本人のプロフィールは、本人の行を更新し、一般公開中の外部アカウントがある場合だけ対象にし（未登録URLの検証が不成立で何も保存しなかった場合は対象にしない）、識別子を失った旧所有者は常に対象にする。purgeは呼び出したエントリーポイントのキャッシュだけに効くため、公開プロフィール専用エントリーポイントのRPC（`purgeProfiles`）から行う。[Workers Cacheのpurge](https://developers.cloudflare.com/workers/cache/purge/)に従う。
- 事前生成した画面はassetsから配信し、`run_worker_first`へAPI・認証・公開プロフィールのパスを登録する。assetsに無いパスは`src/index.ts`のfallbackでTanStack Startが404を返す。公開プロフィールの初回HTMLから`rel="me"`を読めることを確認する。
- staging・Previewでは`run_worker_first: true`により静的ファイルもWorkerへ通し、画面と表示に必要な静的ファイルへBasic認証を適用する。公開プロフィールは外部の相互リンク検証サービスが取得できるよう、Basic認証の対象外とする。API・認証プロトコルのエンドポイントはそれぞれの通常の認証・公開条件で処理する。[静的ファイルのルーティング](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)を参照する。
- API・認証・管理画面の入口は`cache.enabled: false`とし、公開プロフィール専用エントリーポイントだけ`cache.enabled: true`にする。公開プロフィールの応答には、edge用に`cloudflare-cdn-cache-control: max-age=86400, must-revalidate`（TTLの上限1日）、ブラウザー用に`Cache-Control: public, no-cache`を設定し、期限後に古い応答を返さないことを確認する。存在しない・ban中のユーザーの404応答にも同じキャッシュ指示を付け、unban・復元などの後のpurgeで消す。Previewは`cache`設定を継承しないため、公開プロフィールもキャッシュせずに生成する。静的ファイルはassetsのキャッシュを利用する。PreviewのBasic認証を通す入口もキャッシュしない。[Workers Cacheの設定](https://developers.cloudflare.com/workers/cache/configuration/)に従う。
- `cross_version_cache`を有効にする対象では、デプロイをまたいだキャッシュ共有とテンプレート変更時のpurgeを接続する。purgeはキャッシュを保持する公開プロフィール専用エントリーポイントから行い、DB更新後の呼び出しと結果を確認する。入口のキャッシュ設定とブラウザー向けのHTTPキャッシュ制御を分けて確認する。

### Previewとアクセス制御

- [Worker Previews](https://developers.cloudflare.com/workers/previews/)を利用し、PRのpush後に`pnpm exec wrangler preview`でブランチのPreviewを更新する。2026-09-23の公式案内ではWrangler 4.135.0以降が必要となる。
- Previewごとにコード・画面とURLを切り替え、D1などのBindingsは共有可能とする。共有DBへの更新やschema変更は接続先の環境へ共通して反映されるため、動作確認する変更に応じて共有・分離を選ぶ。Preview名ごとのURLとデプロイを固定したURLをPRへ記載する。
- Basic認証を有効にしたテスト環境で、画面と表示に必要な静的ファイルの保護、OAuth往復、各エンドポイントの通常の認証・公開条件によるAPI呼出しを検証する。外部の相互リンク検証サービスによる取得テストは、そのサービスが到達できる検証用URLで行う。
- 外部OAuthのローカル・Preview往復にはOAuth Proxyプラグインを接続し、Providerに登録した安定したcallback URLと許可された戻り先を確認する。

### リクエスト制限と可観測性

- Web検証・一般APIのリクエスト制限をCloudflare WAFのRate Limitingルールへ設定する。Web検証には、AccountsユーザーIDをキーとするWorkers Rate Limiting binding（`URL_VERIFICATION_RATE_LIMITER`。初期値は1分あたり10回、`namespace_id`は環境ごとに分け、Previewはstagingと共有する）も接続し、外部ページの取得とDNS照会の前に適用する。認証endpointはBetter Auth標準のDB保存型Rate Limitを`rateLimit.enabled: true`で有効にし、`advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]`で取得した接続元IPごとに数えることをWorkers上で確認する。
- WAFの対象ホストとパス、カウント対象、閾値、期間、429応答を実環境で確認する。1時間のカウント期間は契約プランの対応を確認してから指定し、採用できる期間と回数を仕様へ反映する。[WAFのプラン別対応](https://developers.cloudflare.com/waf/rate-limiting-rules/)を確認する。
- Workers LogsとTracesを有効にし、`head_sampling_rate`で記録量を調整する。要求URLを記録しないよう、全環境で`observability.logs.invocation_logs: false`とし、アプリケーションが出力するログだけを記録する。`console.log`・`console.warn`・`console.error`で重要度を分け、仕様で許可した項目を構造化JSONとして記録する。[Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)と[Traces](https://developers.cloudflare.com/workers/observability/traces/)を参照する。
- [管理画面と監査](../specification/v0.1/main.ja.md#管理画面と監査)に挙げた監査イベント（ban・unbanを含む）を、仕様で許可した項目だけの構造化JSONとして記録する。
- ソースマップで例外の元ファイルを追えること、秘密情報と利用者データの出力範囲が仕様どおりであることを確認する。

### Workers内の処理

- リクエストごとの状態はハンドラーのローカル変数・引数・Hono contextで渡し、`env`は環境のBindingsの参照に使う。
- 応答に必要な保存・検証は`await`または`return`で完了を待つ。応答後に実行できる処理は`ctx.waitUntil()`へ接続し、実行期限内に完了する単位にする。
- Better Authのバックグラウンド処理もWorkerの実行contextへ接続する。Vite Plusのlintに`typescript/no-floating-promises`を設定する。
- JSON出力は対象の件数に上限があり小さいため、メモリ上で組み立てて直列化し、5MiBを超えないことを確認してから返す。応答前に上限超過を確実に通知できる。
- トークンなどの乱数にはWeb Cryptoの`crypto.randomUUID()`・`crypto.getRandomValues()`を使用する。秘密値の検証は認証ライブラリの標準処理へ委ね、独自比較が必要な箇所では固定長化した値をタイミングに依存しないAPIで比較する。[Workersの実行ガイド](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)を参照する。

## 3. 認証と保存構造を接続する

- [テーブル構造の設計案](../specification/v0.1/main.ja.md#テーブル構造の設計案)から、採用設定でCLI生成したBetter Auth標準schemaとAccounts独自の6表を同じDrizzle schemaに組み合わせる。標準列は生成結果を正とし、公開`oauthClient.clientId`と内部`id`、`account.id`とProviderの`accountId`を区別する。
- Better Auth 1.7系の正式版と対応するDrizzle adapter・OAuth Providerを揃えて導入し、[1.7移行ガイド](https://better-auth.com/docs/guides/1-7-upgrade-guide)から採用版の設定を確認する。

- OAuth tokenの暗号化鍵は、Better Authの`secrets`（versioned secrets。先頭がcurrent）へ環境別のWorker Secretから渡す。新しいversionを先頭に加えて切り替え、旧versionで暗号化したtokenの復号、次回保存でのcurrent versionへの更新、未知versionの拒否を確認する。切り替え手順をREADMEに記載する。
- i18n、Last Login Method、multi-session、OAuth Proxy、Open APIを画面・APIへ接続する。TestUtilsは結合テストとE2Eの準備へ接続する。Adminプラグインは`ac`・`roles`でロール`appAdmin`（`user: ["list", "get", "ban"]`）と権限を持たない`user`を定義し、`defaultRole`を`user`とする。`appAdmin`がユーザーの一覧・取得とban・unbanだけを実行でき、代理ログイン、ユーザーの作成・更新・削除、ロール変更、パスワード設定、セッションの一覧・失効を拒否されることを確認する。
- Google・GitHub・ORCIDの実通信で共通ログインフロー、同一本人・Providerの複数アカウントの明示連携、元ユーザーでの解除後の再連携を検証する。`linkSocial()`・`unlinkAccount()`が標準schema上で期待通りに動作することと、state・nonce・PKCE、暗号化されたProvider tokenの保存を標準の認証経路で確認する。ORCIDとメール未確認のGitHubアカウントも明示連携できることを確認する。`unlinkAccount()`には標準`account`の行ID（`account.id`）を`accountId`として渡す。
- 初めての外部アカウントで標準のユーザー作成とログインが完了し、表示名「仮ユーザー」で利用を開始できることを確認する。`databaseHooks.user.create.before`で`name`を「仮ユーザー」にする。`user.email`には標準処理で作成時の外部アカウントのメールアドレスが入り、その後のログイン・追加連携で変わらないことを確認する。メールを返さないORCIDは、Generic OAuthの`mapProfileToUser`で`{ORCID iD}@orcid.invalid`と`emailVerified: false`を渡す。既存ユーザーの`user.email`と同じメールの未連携の外部アカウントでのログインが`account_not_linked`でログイン画面へ戻って案内が表示され、既存ユーザーでログインして明示連携すれば連携できることを確認する。解除した外部アカウントでの新規登録が同じ結果になり、元ユーザーへの再連携と、移動先ユーザーからの明示連携ができることを確認する。`email_not_found`でも対応する案内が表示されることを確認する。
- 標準`account`の作成・更新後（`databaseHooks.account.create.after`・`account.update.after`）に、外部アカウント行・Provider識別子・`oauth`証明・表示名・本人向けのメール（`external_accounts.email`）を冪等に作成・更新する。公開選択はOFFで作成し、別の所有者の有効な識別子と衝突するユーザー名・プロフィールURLは同じbatchで今回の本人へ移動する。表示名・メールは、Providerの`getUserInfo`を1回呼んで得る。Googleは保存済みのID Token、GitHubは復号したAccess Tokenによる`/user`・`/user/emails`、ORCIDは復号したAccess Tokenによるuserinfoを使う。ORCIDの保存済みID Tokenはnonceが無いと再検証できないため、userinfoだけで取得する。ORCIDはメールを返さないため表示名だけを保存する。書込に失敗した場合は、次回ログイン時のセッション作成後に再構成できることを確認する。
- クライアント登録時に、Accountsのバックエンドが`client_credentials_scopes: ["identities:read"]`を設定し、`clientPrivileges`で必要な`configure-client-credentials-scopes`権限を与える。登録ではアプリ名・リダイレクトURL・`private_key_jwt`用の公開鍵を必須とし、公開鍵はインラインのJWK Setとして標準の登録APIの`jwks`へ渡す。リダイレクトURLに`localhost`・`127.0.0.1`・`[::1]`のHTTPのURLを含む場合は`application_type: "native"`、それ以外は`web`をバックエンドが決め、標準の登録・更新APIへ渡す。HTTPSのloopbackは標準の検査が拒否するため、共有schemaでも拒否する。標準の登録APIへ接続する設定と、利用者の情報提供同意を区別する。[OAuth Provider](https://better-auth.com/docs/plugins/oauth-provider)に従って認可された範囲だけ登録できること、登録したクライアントが`clientRegistrationDefaultResources`により標準の`oauthClientResource`でAccounts資源APIのresourceへ関連付くこと、`oauthProvider.scopes`を`openid`・`identities:read`とし、受け付けるscopeが、Authorization Codeフローの認可要求では`openid`、Client Credentialsのトークン要求では`identities:read`に限られること、UserInfoに`user.email`が含まれないことを確認する。
- OAuth Providerの`consentPage`を「アカウント連携」画面へ接続する。連携先の名前・紹介URL（署名付きクエリの`client_id`を`GET /api/account-links?consentClientId=`へ渡し、有効なクライアントの登録情報を一覧と同じ応答で取得する）と、Accounts共通の定型文（提供する項目と、連携先が公開表示・照合に使いうること）を表示する。画面は「同意して戻る」で今回の連携先への情報提供同意をONにした公開設定を既存の設定保存APIで保存し、保存が成功した後に標準の`oauth2.consent`へ`accept: true`を送る。OAuth要求の検証とコード発行はBetter Authに委ねる。[標準の同意画面](https://better-auth.com/docs/plugins/oauth-provider#consent-screen)を参照する。
- 同意画面の終了操作は、標準`oauth2.consent`の`accept: true`（同意して戻る）と`accept: false`（同意しない）の2つとする。`accept: true`は今回の連携先への情報提供同意をONで保存した後に実行し、認可コードの発行で連携が成立することを確認する。`accept: false`は`access_denied`で元のサービスへ戻り、保存済みの`oauthConsent`と`client_consents`を変更しないことを確認する。同意画面の署名付きクエリは10分で失効するため、失効後の操作では連携を最初からやり直す案内を表示する。
- 利用側が認可要求に`prompt=consent`を付けた場合は、保存済みのOAuth同意があっても同意画面を表示することを確認する。本人が情報提供同意をOFFで保存したときは、同意の保存と同じD1 batchでそのユーザーとクライアントの`oauthConsent`行を削除し、次の認可要求で同意画面が表示されることを確認する。
- 本人の提供先一覧と情報提供状態を、保存済みの同意・公開設定と現在の認可要求から組み立てる。初回選択、設定保存の失敗時、再連携時の保存済み選択を確認する。同意ONで証明済みの選択が0件のクライアントの列と理由を画面に示し、保存の検査と「保存」ボタンの非活性化は画面に表示する有効なクライアントを対象にする。存在しないClient IDの復元設定があっても保存できることを確認する。
- Client Credentialsの署名付きJWT、初回連携、scope・audience、公開鍵の登録・更新をAPIへ接続する。`private_key_jwt`とDPoPは公式OAuth Providerの設定・検証ヘルパーで構成し、利用側の標準ライブラリと接続して確認する。資源APIの検証は`verifyAccessTokenRequest`と同じ標準部品で組み立て、検証鍵を`auth.api.getJwks()`から読む。Authorization CodeとClient CredentialsのAccess Tokenの`expires_in`が900秒になること、`/token`が無効でセッション応答にJWTヘッダーが付かないことを確認する。
- 公開鍵の更新と紹介URLの削除は、承認済みの独自拡張として、所有者本人のクライアントの`oauthClient`の`jwks`・`uri`をAccountsの保存処理で更新する。鍵は標準の登録時と同じ検査関数（`@better-auth/oauth-provider/internal`の`validatePublicClientJwks`。公開APIの互換保証外）で検査し、JWK SetをJSON文字列で保存する。保存は鍵の検査、標準の更新API（`adminUpdateOAuthClient`）でのアプリ情報・リダイレクトURLの更新、鍵・紹介URLの保存の順に行う。鍵の保存だけが失敗した場合に同じ内容の再保存で収束すること、次のクライアント認証から新しい鍵で検証されること、新旧の鍵を同じJWK Setに含めて切り替えられることを確認する。Better Authの版を更新するときは、この検査関数の挙動をテストで確認する。
- 標準の`rateLimit`表と採用プラグインのschemaを生成し、独自表のPK・FK（`ON DELETE CASCADE`）・本人内UNIQUE・有効識別子の部分UNIQUE・検索索引をmigrationへ含める。認証用の標準表には採用版の実際の検索に必要な索引を確認する。生成したDrizzle relationsをadapterに渡し、同じ表間に複数の関連がある箇所は`relationName`を対応させる。
- 未検証URLの複数人登録、本人内150件、有効識別子の一意性、証明と複数識別子の対応、再検証失敗時の成功集合維持、Web識別子だけの移動、リンク証明単独では`dns_txt`・`oauth`が支える識別子を移動しないこと、OAuth解除で他方式の証明が残る場合、支えを失った識別子が`is_active=0`の候補になること、最後のログイン手段の解除拒否を保存層の検証対象にする。
- 標準`unlinkAccount()`の`account`行削除で、対応する`oauth`証明と対象関連が外部キーのCASCADEにより同じ文で削除され、ほかの証明・識別子・外部アカウント行が残ることを確認する。標準`deleteUser`の`user`行削除では、本人の独自表データが同じ文で削除される。支える成功証明が無くなった識別子は、後続のbatchで`is_active=0`の候補にする。表示行全体の解除は標準の解除を先に行い、成功した場合に後続のbatchで`external_accounts`行を削除する。最後のログイン手段などで標準の解除が拒否された場合は、独自表を変更しない。
- すべての日時をUTCとして保存し、Drizzle・Better Auth・JSON境界で単位とUTCの往復を確認する。
- 一覧・照合の読取条件と、公開設定保存・所有者移動・復元の一括書込を[読み取りと更新の単位](../specification/v0.1/main.ja.md#読み取りと更新の単位)に合わせる。複数の値は配列をJSON文字列にした1つのバインド値で渡し、`json_each(?)`で展開する（読取は`IN (SELECT value FROM json_each(?))`、復元の書込は`INSERT … SELECT … FROM json_each(?)`）。照合は入力を500件ずつ読み、`json_each`の`key`で元の入力順へ戻す。1操作の原子性が必要な書込は1回の`batch()`に収める。

### D1のmigrationと運用コマンド

- Drizzle Kitでschema差分からmigration SQLを生成し、Wranglerが読むmigrationディレクトリに保存する。
- Better Authの標準schemaは`pnpm auth:generate`で生成し、手編集しない。生成schemaに無い`account(provider_id, account_id)`の一意索引は、`pnpm db:generate --custom`で作るmigrationへ`CREATE UNIQUE INDEX`を書いて追加する。
- 独立したデータ移行SQLが必要な場合は`pnpm exec wrangler d1 migrations create <DATABASE> <MESSAGE>`で作成し、同じ履歴に含める。
- ローカルで`pnpm exec wrangler d1 migrations apply <DATABASE> --local`を実行し、stagingで`--remote --env staging`を指定して検証する。
- `pnpm exec wrangler d1 execute <DATABASE>`はSELECT、確認用SQL、シード、単発の保守処理に使い、実行環境を明示する。
- schema・索引変更後に`PRAGMA optimize`を実行する。[D1のSQL仕様](https://developers.cloudflare.com/d1/sql-api/sql-statements/#pragma-optimize)と[Wrangler D1コマンド](https://developers.cloudflare.com/workers/wrangler/commands/d1/)を参照する。
- 生成したmigrationをバージョン管理し、空DBと変更前schemaの双方から適用できることを確認する。
- D1では外部キーを無効にできず、親表を作り直すmigrationの`DROP TABLE`はCASCADEで子表の行を消しうる。該当するmigrationは、データを入れたstagingで適用前後の件数を確認する。

## 4. Accountsの機能を実装・移管する

- [URL検証仕様](../specification/v0.1/verify-url.ja.md)から、単一URL入力後の「保存して検証する」押下を起点とした未登録URLの受付、取得と証拠抽出、リンク検証が成立しない場合の同一要求内でのDNS TXT確認、結果の保存、保存済み識別情報による照合を実装する。成功時に入力URLを登録し、未登録URLで両方法が不成立なら登録せず方法別の結果を返して「未検証で保存」を案内する。「未検証で保存」ボタンを押した場合だけ未検証として登録する。登録済みURLの再検証の失敗では直近の試行結果だけを更新する。移行元の既存テストを新しい条件へ対応付ける。CDNでキャッシュされた応答（`Age`・`CF-Cache-Status`を持つ応答）も通常の応答として扱う。
- セッション本人のプロフィールURLを期待値とし、入力URLの構文・取得先の安全性を検査してから公開ページを取得する。リンクが成立すればその成功結果を保存し、取得失敗・リンク不一致などで成立しなければ対象hostのDNS TXTを確認する。DNS成功時は、入力URLと同じhostの登録済みURLを含む各外部アカウントに、hostをキーとする`dns_txt`証明行を作る。外部アカウントは統合しない。直近の方法別再検証結果と有効な証明・紐付けを分け、照合APIは保存済みの識別子・証明・現在の紐付け・公開許可で判定する。
- DNS TXTは、Workersの`node:dns/promises`の`resolveTxt`（`cloudflare-dns.com`（1.1.1.1）へのDNS over HTTPS。subrequestとして数える）で`_accounts.{host}`を照会する。照会の期限は3秒とし、ページ取得の5秒とは別に数える。各レコードのcharacter-stringを連結してURL正規化を適用し、本人の公開プロフィールURLとの完全一致を判定する。CNAMEの行は無視する。該当するTXTが無い場合と`ENOTFOUND`・`ENODATA`（NXDOMAIN・NODATA。Workersの実装は回答の無い応答をすべて`ENOTFOUND`とするためSERVFAILを含む）は`not_verified`、DNS over HTTPSのHTTP・通信の失敗（`EBADRESP`・`EBADQUERY`）とtimeout、期待するURLと同じAccountsサービスの異なるユーザーの公開プロフィールURLが併存する場合は`indeterminate`とする。CNAMEを設定したサブドメインでも`_accounts.{host}`のTXTで証明できること、既存のTXTを残したまま証明できること、追加直後の不一致で再検証を促す案内が出ることを確認する。「アカウント連携」画面の入力欄の近くに、本人の公開プロフィールURL（TXTの値を兼ねる）とコピー操作を表示する。
- セッションから本人とプロフィールURLを決定し、正規化、HTML全体の許可リンク・テキスト、HTTP Link、サービス別の公開ページ解析を検証する。GitHub・GitLab・Stack Overflow・Qiita・note・Zenn・Codeberg・X・Hugging Faceのプロフィールに個別対応し、サービス名の判定、redirect追跡後の最終取得URLへのURL規則の適用によるユーザー名の抽出、そのプロフィールページの証拠による証明を実装する。組織アカウントのプロフィールURLも個人と同じ規則でサービス名とユーザー名を保存する。記事・投稿・Gist・Merge Request・Issue・質問・回答・リポジトリ・モデル・データセット・SpacesなどのコンテンツURLと、Reddit・KaggleのURLは汎用Webページとして登録・共通検証し、証明は入力URL単独に適用する。第三者投稿の読者コメントと`code`・`pre`内のコード例のURLも証拠候補に含め、異なるAccountsユーザーへのURLが併存する場合の判断不能を確認する。HTTPステータスは404・410を`not_verified`、401・403・429と5xxなどのその他を`indeterminate`とする。コンテンツURLの証明が作者のユーザー名・プロフィールURLへ適用されないこと、リンク検証の結果表示がページの編集権限を確認したように見えないことも確認する。
- `HTMLRewriter`はテキストと属性値の文字参照（`&lt;`・`&amp;`・`&#x26;`など）を復号しない。テキストノードのチャンクを連結してから文字参照を復号してlinkify-itへ渡し、`href`などの属性値も復号してから相対URLを解決・正規化する。抽出はチャンクを連結したテキストノード単位で行い、要素やコメントをまたいで連結しない。`template`・`noscript`の中身は除外し、`hidden`属性やCSSによる表示状態は評価しない。`code`・`pre`内の`&lt;URL&gt;`形式のURLが一致することをテストする。
- [管理画面](../specification/v0.1/main.ja.md#管理画面と監査)の設定・アカウント連携・開発者向けへ機能を配置する。個別の公開先選択、一括指定、保存ボタンの状態、保存APIの検証を接続する。本人向けの外部アカウント一覧には、取得できた場合はOAuthのメールアドレスを、無い場合は表示名だけを表示する。
- 「アカウント連携」画面に「OAuthの認証連携だけ解除する」操作を置き、標準`unlinkAccount({ accountId })`（`accountId`は標準`account`の行ID）を呼ぶ。対応する`oauth`証明と対象関連だけが終了し、ほかの方法が支える識別子と外部アカウント行が残ること、最後のログイン手段の解除が標準どおり拒否されることを確認する。
- 公開プロフィールを未ログインで取得し、許可された情報と検証方法のバッジが初期HTMLに含まれることを確認する。
- 公開プロフィールの初回取得でD1からHTMLを生成し、再取得ではWorkers Cacheから返すことを確認する。外部リンク0件でも表示名・固定IDを返し、退会後とban中は404となることを確認する。公開設定・外部アカウント解除・所有者変更・退会・ban・unbanによるDB更新後は、対象プロフィールのpurgeと次の取得での公開内容の再評価を確認する。
- [運営者の権限](../specification/v0.1/main.ja.md#運営者の権限)に従い、運営者機能は画面を設けず、ログイン済みの`appAdmin`がAdmin APIを呼ぶ。初回の`appAdmin`は、OAuthで作成したユーザーの`user.role`を`pnpm exec wrangler d1 execute`で`appAdmin`に更新して任命する。banは期限を指定せずに行う。ban中はログインの拒否と既存セッションの削除（標準）、公開プロフィールの404、連携アカウント一覧と照合APIでユーザーが存在しない場合と同じ結果になり、unbanで元の公開設定へ戻ることを確認する。
- OAuthクライアント管理を接続し、登録件数上限、提供先としての表示、Client ID・公開鍵、登録情報の編集・削除を仕様からテストする。本番のHTTPSとloopbackのリダイレクトURLを1つのクライアントに併記できること、loopbackのHTTPはportだけを除いて一致を確認すること、`application_type`にかかわらず`private_key_jwt`・`client_credentials`・DPoPを使えることを確認する。
- [Accounts API](../specification/v0.1/main.ja.md#accounts-api)の入力・出力スキーマ、HTTPメソッド、認証・認可、不正な入力を含む場合の400応答を実装する。
- Valibotの共通スキーマを公式`@valibot/to-json-schema`で変換し、OpenAPI 3.2.1の`query`操作・認証（`private_key_jwt`とDPoPのClient Credentials）・応答定義（照合のHTTP 400は`results`と最上位`errors`の2形式）へ組み込み、`GET /api/v1/openapi.json`で認証なしに配信する。Better AuthのOpen APIプラグインが出力する認証API（OpenAPI 3.1.1、`/api/auth/reference`のScalar表示）は認証APIの文書だけを埋め込むため、資源APIの文書は開発者向け画面に操作ごとの見出し・経路・要求と応答のschemaとして表示し、JSONへのリンクと並べて認証APIと区別して案内する。資源APIの送信は利用側の契約テストで確認する。[ValibotのJSON Schema変換](https://valibot.dev/guides/json-schema/)、[HonoのQUERY対応](https://github.com/honojs/hono/releases/tag/v4.13.0)を参照する。
- [JSONによるバックアップと移行](../specification/v0.1/main.ja.md#jsonによるバックアップと移行)から、出力前の内容確認・復元ボタン・設定反映・登録候補を実装する。存在しないクライアントIDを含む公開設定も確定した保存方式で取り込む。件数上限（`externalAccounts`は300件、各アカウントの識別子・証明は各20件、`clientConsents`は50件、`clientVisibility`は`clientConsents`にあるClient IDだけ）を入力検査に含め、`json_each`による`INSERT … SELECT`で1回の`batch()`に書き込む。1つのバインド値は1,000,000 bytes以内に分け、文の数は入力件数ではなく容量だけで増える。
- [退会](../specification/v0.1/main.ja.md#accountsユーザーの退会)を、標準`deleteUser`による認証削除と、外部キーのCASCADEによるAccounts独自データの削除へ接続する。`session.freshAge: 0`により解除・退会がログインからの経過時間を問わず有効なセッションで実行でき、`deleteUser`が確認メールを使わず退会確認画面での確定後に即時削除することを確認する。
- 連携解除・退会の後もGoogle・GitHub・ORCIDの連携アプリ一覧にAccountsが残り、各サービスの設定から本人が取り消せることを公開ヘルプで案内する。

- PRのpushでPreviewを更新し、実行した検証コマンドと結果をPRへ記載する。失敗や未検証項目は完了済みと区別する。

### READMEに追加する手順

1. リポジトリで`pnpm install`を実行する。
2. Accountsのディレクトリで`pnpm exec wrangler login`を実行する。
3. `pnpm exec wrangler d1 create <DATABASE_NAME>`で環境用DBを作成する。
4. `wrangler.jsonc`の名前・DB ID・Bindings・環境設定を実際の値へ合わせる。
5. `.env.example`からローカル環境を用意し、デプロイ先へ`pnpm exec wrangler secret put <NAME> --env staging`で秘密値を登録する。
6. migrationを適用し、Bindings型を生成する。
7. 通常の画面開発はVite Plusの開発scriptで起動する。Worker単体の確認には`pnpm exec wrangler dev --env staging`を使い、遠隔の実行環境を確認する場合は対象環境を指定して`--remote`で起動する。
8. 型検査・lint・単体・Workers結合テストとビルドを実行し、ローカルpreviewで成果物を確認する。
9. `pnpm exec wrangler preview`でPRのPreviewを更新し、Basic認証とOAuth設定を含めて利用フローを確認する。
