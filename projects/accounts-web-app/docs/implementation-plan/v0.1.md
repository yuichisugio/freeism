# Accounts v0.1 実装計画

## 実装の入力

[v0.1仕様](../specification/v0.1/main.md)の確定事項と受け入れ条件に従って、下記の移管・接続作業を行う。
仕様の未決事項を実装前に確認し、各フェーズで必要な項目を確定する。
移行準備時に、下記モジュールの実装状態、各環境のデプロイ状況、保存済みデータの有無を確認する。

外部アカウントの管理機能に付随するDB定義、設定値、OAuthコールバック、シークレット、監視、テストも移行対象の棚卸しに含める。

- [外部識別情報](../specification/v0.1/main.md#外部識別情報の仕様)と[Webページの検証](../specification/v0.1/main.md#webページの検証仕様)を、照合・リンク検証の実装に使用する。
- [サービス間の境界](../specification/v0.1/main.md#pointsなどの連携サービスとの境界)を確認してPoints側の接続箇所を特定する。

Points側の経済処理との接続は、[Pointsの未受領FIX仕様](../../../points-web-app/docs/v0.2/details-ja/unclaimed-fix-and-ownership.md)と[Points実装計画](../../../points-web-app/plan/v0.2-implementation.md)を参照して作業する。

## 実装順序

### 1. 接続契約と移行対象を確定する

- [仕様の未決事項](../specification/v0.1/main.md#未決事項)を整理し、API契約を確定する。
- 採用するBetter Auth OAuth Providerのバージョンと対応する設定を確認し、[クライアント認証と権限](../specification/v0.1/main.md#クライアント認証と権限)のトークン発行・検証・scope設定を実装へ対応付ける。
- [ORCIDの認証連携](../specification/v0.1/main.md#提供技術要件)について、採用するBetter Auth Generic OAuthのバージョンとORCIDのendpoint・scope・応答を確認し、固有ID・取得できる表示名の対応付けと、登録・ログイン・明示連携の設定を具体化する。
- [外部認証情報](../specification/v0.1/main.md#外部認証情報)の解除完了条件を、各Providerの失効APIへ対応付ける。[Google](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke)の失効範囲・Refresh Tokenの扱いと、[ORCID](https://info.orcid.org/ufaqs/how-can-i-revoke-tokens/)のtokenペアの失効・成功時と既失効時の応答を確認し、判定方法を具体化する。
- 要件定義がすべて確定した後に、Accountsのテーブル構造・一意制約・関連・索引を設計する。設計結果からmigrationとテストの作成へ進む。
- 表の移行元から呼出元を追い、認証フック、CSV照合、未受領分の受領、プロフィール表示、アカウント閉鎖・再開、定期処理まで移行対象を確定する。
- ソースコードの移管と利用者の利用開始手順を分け、[利用開始の流れ](../specification/v0.1/main.md#利用開始の流れ)に従ってAccountsへの新しい登録・証明・公開先設定を案内する。各環境のデータ有無・稼働状態を確認して切り替え手順を定める。

### 2. Accountsの仕様からテストを作成する

- [受け入れ条件](../specification/v0.1/main.md#受け入れ条件)を各テストケースへ対応付ける。
- 移行元のURL正規化・リンク抽出・安全取得のテストを棚卸しし、Accounts側のテストへ移管する。
- 単体テストと、認証・DB・APIの境界を確認する結合テストを分ける。実装前に期待した失敗を確認する。

### 3. Accountsへ機能を移管する

- 外部認証・紐付け、共通のWebページ取得・リンク検証、公開プロフィール、公開設定、照合APIを仕様に従って実装する。
- [操作の認可](../specification/v0.1/main.md#操作の認可)に従って、通常のセッションから操作主体を確認し、対象データ・操作への権限を検証する処理を実装する。未ログイン・権限なしの拒否と、本人による各管理操作の成立をテストする。
- [登録・ログインと外部アカウントの所有権証明](../specification/v0.1/main.md#v01で実装する機能)に従ってORCIDの認証連携を追加し、認証情報・callback設定・画面・保存処理を接続する。新規登録、ログイン、同一サービスの複数アカウントの追加連携、一意性、最後のログイン手段の保持、公開範囲をテストで確認する。
- [外部認証情報](../specification/v0.1/main.md#外部認証情報)に従ってGoogle・GitHub・ORCIDの連携解除を実装する。外部失効を確認してから保存token・紐付けを削除する処理、未完了の表示、本人の再実行を接続し、失効成功・既失効・通信失敗の条件をテストする。
- [クライアント認証と権限](../specification/v0.1/main.md#クライアント認証と権限)に従って初回連携の認可フロー・本人確認、トークン発行・API認証を実装し、Client ID・Client Secretの管理画面と接続する。
- 同仕様に従ってJWTの検証鍵の読込・更新と検証処理を実装し、クライアント単位の失効確認・現在の提供許可のDB照合へ接続する。不正なJWTをDB照合前に拒否できることと、Secret再発行後の即時失効をテストで確認する。
- [Accountsユーザーの退会](../specification/v0.1/main.md#accountsユーザーの退会)に従って、退会画面と本人・登録OAuthクライアントの終了・削除処理を実装する。
- [管理画面と監査](../specification/v0.1/main.md#管理画面と監査)に従ってログ出力を整備し、認証ライブラリ・リクエスト処理・例外処理の出力を検証する。
- JSONエクスポートと本サービスでのバックアップ復元を実装し、[バックアップと移行の仕様](../specification/v0.1/main.md#jsonによるバックアップと移行)に対応するテストを実行する。
- 所有権証明を受領・ポイント計上処理から分離し、Accountsが担当する画面・API・保存処理を揃える。
- [外部識別情報の仕様](../specification/v0.1/main.md#外部識別情報の仕様)と[Webページの検証仕様](../specification/v0.1/main.md#webページの検証仕様)に対応する実装差分を確認する。
- 対応する単体・結合テスト、型検査、静的検査を実行する。

### 4. Pointsの利用側を切り替える

- [利用開始の流れ](../specification/v0.1/main.md#利用開始の流れ)に従って、Points運営者がAccounts互換サービスのURLとOAuthクライアント情報を設定できるようにし、設定済み接続先を選ぶ画面と認可フローへ接続する。Client Secretのバックエンド管理を確認する。
- 同仕様に従って接続先の取り下げ処理を実装し、対象Accountsサービスへの既存のユーザー間の対応とAPI利用が終了すること、Accounts側の公開設定・情報提供同意とPointsの確定済み貢献・ポイントが維持されることを確認する。
- CSV検証・確定、未受領分の受領、プロフィール、アカウント閉鎖・再開など、外部アカウントに依存する処理を確定したAccounts API契約へ接続する。
- PointsのCSVで指定する識別子の形式を確定し、URL・外部サービス名と固有ID・AccountsユーザーIDをAccounts APIへ渡す入力処理と確認画面を実装する。
- Points側の外部アカウント管理の導線をAccountsへ向ける。
- [サービス間の境界](../specification/v0.1/main.md#pointsなどの連携サービスとの境界)に従って、Pointsでユーザー間の対応を解除する処理を実装し、Accounts側の公開設定・情報提供同意とAPIの提供範囲が維持されることを結合テストで確認する。
- Accountsの一覧取得APIをPointsのプロフィール・公開APIへ接続し、提供を許可した外部アカウントの表示を確認する。
- [サービス間の境界](../specification/v0.1/main.md#pointsなどの連携サービスとの境界)に従い、独立した認証と情報連携を結合テストで検証する。
- Pointsの未受領分・確定済み貢献に関する回帰テストを実行する。

### 5. 移管を完了する

- Accountsでの機能提供とPointsからの利用を確認し、Points内の移管済み処理・画面・APIを整理する。
- 移管元の所有権管理に付随する処理・Cron・監視・DB定義の呼出関係を確認し、仕様に定めた現在の紐付け管理とPointsの経済履歴に合わせて整理する。
- 両アプリの仕様・実装計画・テスト・設定手順を、切り替え後の責務に合わせて更新する。

## 検証の実行と完了確認

- 各フェーズで単体テスト、結合テスト、型検査、静的検査の結果を記録する。実行コマンドは実装時点の各アプリのpackage scriptsを確認して選ぶ。
- [受け入れ条件](../specification/v0.1/main.md#受け入れ条件)とテスト結果を突き合わせ、未検証項目を確認する。
- 移行元モジュールの呼出元を再検索し、Points側の参照・設定・監視の整理漏れを確認する。
- 変更したMarkdownの相対リンクと仕様参照を検査し、実装差分と文書を独立レビューする。
