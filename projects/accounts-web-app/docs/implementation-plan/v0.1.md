# Accounts v0.1 実装計画

## 目的と位置付け

`points.freeism.app`に実装されているAccountsの責務に属する機能を、リンク検証を含めてすべて`accounts.freeism.app`へ移行する。
対象には、外部アカウントの認証・連携・所有権証明・識別・公開設定と、それらを支える画面、API、保存処理、外部サービス設定、テストを含む。
移行後はAccountsが外部アカウントとAccountsユーザーの対応を管理し、PointsはAccounts APIの照合結果を利用して貢献データとポイントを管理する。

要件の正本は[v0.1仕様](../specification/v0.1/main.md)とする。
本計画は機能移管の範囲と進め方を定めるものであり、要件定義の対話で未決事項を確定してから実装へ進む。
下記の移行元には対応する実装が存在するが、デプロイ状況・保存済みデータの有無は移行準備時に確認する。

## リンク検証の移行方針

1. 本人がAccountsへ外部ページのURLを登録する。
2. 外部ページへ設置するリンク先として、`https://accounts.freeism.app/profiles/{accountsUserId}`を案内する。
3. 本人による検証操作を受け、Accountsのバックエンドが外部ページを取得する。
4. Pointsのリンク抽出・URL照合処理を再利用し、本人のAccounts公開プロフィールURLとの一致を検証する。
5. 成功したURLをAccountsユーザーへ紐付ける。公開プロフィールへの掲載とOAuthクライアントへの提供は、それぞれの公開設定に従う。

リンク抽出の移行元は、HTMLの`a[href]`・`link[href]`とHTTPの`Link`ヘッダーを対象とし、`rel=me`を優先して正規化後のURL完全一致を検証する実装である。
外部ページの取得制限、リダイレクトの検査、リンク抽出、照合条件は、既存テストとともに移管して検証する。
所有権の有効性はAccounts仕様に合わせ、登録時の検証から本人の解除まで有効な現在の紐付けとして管理する。

参考: [Pointsの所有権仕様](../../../points-web-app/docs/v0.2/details-ja/unclaimed-fix-and-ownership.md)、[公開プロフィール仕様](../../../points-web-app/docs/v0.2/details-ja/profile-setting.md)、[Points実装計画 Task 9〜10](../../../points-web-app/plan/v0.2-implementation.md)。

## Pointsとの接続

- Pointsは、Accounts APIへプロフィールURL、外部サービス名と固有ID、またはAccounts IDを渡し、確定したAPI契約に従って貢献者を識別する。
- 外部アカウントによる照合は、照合時点で有効なPointsへの公開許可に従う。第三者のアップロード時やバックグラウンド処理時にも利用できる。
- 貢献データ、FIX、未受領分の受領操作、ポイント台帳・残高と確定済みの帰属はPointsが管理する。
- Pointsのプロフィールに含まれるパッケージ、残高、経済履歴とそれらの公開設定は、Pointsの責務として維持する。
- Marketsなどへ経済情報・操作権限を提供するPointsのOAuth資源APIは、Pointsの責務として維持する。Accountsの識別情報を提供するOAuth Providerとの認証・認可の境界を定める。

## 実装順序

### 1. 接続契約と移行対象を確定する

- 下記の実装前に確定する事項を整理し、Accounts APIの入出力・認証・公開許可・エラー時の扱いを仕様に記載する。
- 表の移行元から呼出元を追い、認証フック、CSV照合、未受領分の受領、プロフィール表示、アカウント閉鎖・再開、定期処理まで移行対象を確定する。
- ソースコードの移管と保存済みデータの移行を分け、各環境のデータ有無・稼働状態に応じて切り替え手順を定める。

### 2. Accountsの仕様からテストを作成する

- 外部アカウントの一意性、追加連携、連携解除後の再登録、最後のログイン手段を残す条件をテストする。
- 本人の公開プロフィールに向いた証明リンクの成功と、別のAccountsユーザーへのリンク・単なるURL文字列・取得失敗の不成立をテストする。
- 外部ページを公開プロフィールに掲載する設定と、所有権の検証を独立してテストする。
- 公開先ごとの外部アカウント選択、Googleメールの本人向け表示、公開解除後の照合結果をテストする。
- 単体テストと、認証・DB・APIの境界を確認する結合テストを分ける。実装前に期待した失敗を確認する。

### 3. Accountsへ機能を移管する

- 外部認証・紐付け、Webページのリンク検証、公開プロフィール、公開設定、照合APIを実装する。
- 所有権証明を受領・ポイント計上処理から分離し、Accountsが担当する画面・API・保存処理を揃える。
- 一意性、再連携、検証の有効性、テキスト情報の取り扱いはAccountsの確定仕様に合わせる。
- 対応する単体・結合テスト、型検査、静的検査を実行する。

### 4. Pointsの利用側を切り替える

- CSV検証・確定、未受領分の受領、プロフィール、アカウント閉鎖・再開など、外部アカウントに依存する処理を確定したAccounts API契約へ接続する。
- Points側の外部アカウント管理の導線をAccountsへ向ける。
- PointsユーザーとAccountsユーザーの対応、Pointsのセッション、重要操作の再認証を、確定した方針に従って接続する。
- 未受領分の帰属と、既に確定した貢献・ポイントを維持する回帰テストを実行する。

### 5. 移管を完了する

- Accountsでの機能提供とPointsからの利用を確認し、Points内の移管済み処理・画面・APIを整理する。
- 所有権の定期再検証、失効処理、関連するCron・監視・DB定義も呼出関係を確認し、AccountsのライフサイクルとPointsの経済履歴の責務に合わせて整理する。
- 両アプリの仕様・実装計画・テスト・設定手順を、切り替え後の責務に合わせて更新する。

## 実装前に確定する事項

- PointsのログインをAccountsへ接続する方式、Points IDとAccounts IDの対応、重要操作の再認証と管理者判定。
- Accountsの現在の紐付けを使った、Pointsの未受領FIXの帰属ルール。外部アカウントの紐付け先変更時も含めて定める。
- 照合APIを呼ぶOAuthクライアントの認証方式、権限、APIが利用できない場合のPoints側の扱い。
- GitHub・Webページの表示項目、URLと固有IDの対応、Accountsの残りのv0.1要件。
- 保存済みのユーザー・外部アカウント対応・公開許可の移行要否と、必要な場合の再証明・再同意の手順。

## 完了条件

- Accountsの責務に属する既存機能が、関連する画面・API・保存処理・設定・テストを含めてAccountsで提供されている。
- Pointsで行う第三者の貢献データ登録・照合が、Accountsの有効な公開許可に基づいて成立する。
- 外部アカウントの追加・解除・公開設定の変更と、Pointsの確定済み貢献・ポイントの維持が、仕様に基づくテストで確認できる。
- PointsからAccountsへ切り替えるすべての呼出元と関連設定が確認され、担当する責務が両アプリの文書と実装で一致している。
