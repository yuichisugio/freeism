# Accounts v0.1 実装計画

## 実装の入力と進め方

[Accounts v0.1仕様](../specification/v0.1/main.ja.md)と[URL検証仕様](../specification/v0.1/verify-url.ja.md)の確定事項・受け入れ条件を入力とし、以下の実装・移管・検証を進める。
要件と振る舞いは仕様書に集約し、この文書では作業順序、導入手順、確認方法を管理する。
未決事項は対応する実装に着手する前に確定し、テーブル構造を更新してからmigrationを作成する。
既存コードは移管対象を調べる資料として扱い、採用する構成は現行仕様と標準機能から決める。
実装の構造や細部は、利用者の目的と保守性を満たす、より良い方法を柔軟に選ぶ。サブエージェントには成果物と担当範囲を渡し、調査・実行の進め方は担当へ任せる。
Sol 6のサブエージェントは調査、文書記載、実装、レビュー、PR更新を担当する。Astra 6のメインエージェントは全体を管理し、レビュー結果と実装差分を敵対的にレビューする。指摘は現実的な利用フローでトリアージし、修正要否を判断する。
この要件定義の対話中は、回答を仕様書へ反映してレビューを省略する。実装・PRなどのレビュー方針は、その作業時に適用する。
認証の追加拡張が必要になった場合は、標準機能で満たせない理由と追加案を整理し、ユーザーの承認後に実装する。

- v0.1の実装は専用の`codex/`ブランチで進め、PRを作成し、そのPRのブランチへ実装・テスト・文書の変更をpushする。
- 初期の実装差分をdraft PRとして共有し、以後のpushで更新する。PRに仕様参照、検証結果、Preview URLを記載する。
- フェーズごとに最小の動作単位を実装・検証する。ユーザーの権限、所有者の一意性、保存結果に必要なチェックをバックエンドに置く。
- Pointsとの接続変更は[Points実装計画](../../../points-web-app/plan/v0.2-implementation.md)と連携する。

## 1. 開発基盤と構成を整える

- Valibot、Hono、Drizzle、Better Auth、TanStack Start、React、HeroUI v3、Tailwind CSS、Vite Plusを導入する。依存関係は既存のpnpm運用で管理し、必要に応じて適切な版へ更新する。
- [提供・技術要件](../specification/v0.1/main.ja.md#提供技術要件)に従い、HonoのHTTP境界、機能ごとの処理、DrizzleによるDBアクセスを分ける。外部接続の差し替えとテストに必要な境界に絞ってクリーンアーキテクチャを適用する。
- フロントエンドは機能単位のディレクトリにビューとフックを分ける。API呼出し、状態管理、保存・検証操作を機能ごとのフックに集約し、ビューは受け取った状態と操作を描画へ結び付ける。
- 入出力のValibotスキーマを共通モジュールへ置き、画面入力とHonoの入力境界の両方で同じ検証を実行する。セッションの本人確認とDB上の権限確認はバックエンドで行う。
- TypeScriptの`strict`を有効にし、Better Authの`$Infer`とHonoのルート型から型を取得する。
- Hono 4.13.0以降の`app.query()`を使い、APIのPATHとハンドラーを同じ宣言にまとめる。機能別のルートファイルは`app.route()`で接続し、型推論を保つ。[Honoの構成ガイド](https://hono.dev/docs/guides/best-practices)を参照する。
- [Cloudflare Vite PluginとTanStack Startの公式構成](https://developers.cloudflare.com/workers/framework-guides/web-apps/tanstack-start/)を接続する。TanStack StartのSPA・事前生成設定を使用し、画面の生成物をassetsへ接続する。`src/index.ts`のHonoはAPI・認証・公開プロフィールのSSRを担当し、Vite Plus経由の開発・ビルド・プレビューを整える。

## 2. Workersの実行・配信・運用環境を整える

### WranglerとBindings

- `wrangler`をアプリの`devDependencies`へ追加する。Worker Previewsに必要な版を満たす最新版を選び、プロジェクト内のCLIで実行する。
- `wrangler.jsonc`に`main: "src/index.ts"`、`minify: true`、`upload_source_maps: true`を設定する。
- `compatibility_date`を導入時の最新日付にし、`compatibility_flags: ["nodejs_compat"]`を指定する。日付・flagを更新した差分でビルドとWorkers上のテストを実行する。
- `placement: { mode: "smart" }`を設定し、D1アクセスと公開画面の応答時間を確認する。静的アセットをWorker経由にした場合の配置の影響も計測する。
- 本番・stagingの変数、D1、Secret、認証callbackを環境別に設定し、Preview用の`previews`設定を整える。
- `pnpm exec wrangler types --env-interface CloudflareBindings`で`worker-configuration.d.ts`を生成し、`tsconfig.json`の`compilerOptions.types`へ接続する。環境設定の更新後も型を再生成する。
- 型検査scriptを`pnpm exec wrangler types --env-interface CloudflareBindings && tsc --noEmit`として登録する。
- デプロイ先の秘密値は`pnpm exec wrangler secret put`で登録する。ローカルではgit管理外の`.env.local`またはシェル環境から読み込み、必要な変数名と説明を`.env.example`へ記載する。[環境変数の公式手順](https://developers.cloudflare.com/workers/local-development/environment-variables/)に従って、選択した環境での読み込みを確認する。

### 静的ファイル・公開HTML・キャッシュ

- JS、CSS、画像、事前生成した画面をWorkersの`assets`へ接続する。出力先はCloudflare Vite Pluginが生成する配信設定と揃える。
- API、OAuth関連endpoint、`/.well-known/*`をWorkerで処理する。`/profiles/*`は公開プロフィール専用エントリーポイントへ渡し、キャッシュミス時にHonoがD1から在籍ユーザーの表示名・固定IDと一般公開を許可された外部アカウント情報を読み、HTMLをSSRして`c.html()`で返す。公開する外部リンクが0件でもプロフィールを返し、退会などでユーザーが存在しない場合は404を返す。[HonoのHTML応答](https://hono.dev/docs/api/context#html)、[Workers Cache](https://developers.cloudflare.com/workers/cache/)を参照する。
- 表示名・外部アカウントの一般公開設定の変更、外部アカウントの解除・所有者の変更・退会など、プロフィールの表示内容に影響するDB更新後、影響するプロフィールのWorkers Cacheをpurgeする。所有者の変更では旧・新双方のプロフィールを対象にする。次の取得でD1からユーザーの存在と公開対象を読み直してHTMLまたは404を返す。テンプレート変更時もキャッシュをpurgeする。[Workers Cacheのpurge](https://developers.cloudflare.com/workers/cache/purge/)に従う。
- SPAモードを用いる画面は`not_found_handling: "single-page-application"`で配信し、`run_worker_first`へAPI・認証・公開プロフィールのパスを登録する。固定ページのSSG生成物はassetsから配信し、公開プロフィールの初回HTMLから`rel="me"`を読めることを確認する。
- staging・Previewでは`run_worker_first: true`により静的ファイルもWorkerへ通し、画面と表示に必要な静的ファイルへBasic認証を適用する。API・認証プロトコルのエンドポイントはそれぞれの通常の認証・公開条件で処理する。[静的ファイルのルーティング](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)を参照する。
- API・認証・管理画面の入口は`cache.enabled: false`とし、公開プロフィール専用エントリーポイントだけ`cache.enabled: true`にする。公開プロフィールのHTML応答に公開キャッシュ用の`Cache-Control`を設定し、静的ファイルはassetsのキャッシュを利用する。PreviewのBasic認証を通す入口もキャッシュしない。[Workers Cacheの設定](https://developers.cloudflare.com/workers/cache/configuration/)に従う。
- `cross_version_cache`を有効にする対象では、デプロイをまたいだキャッシュ共有とテンプレート変更時のpurgeを接続する。purgeはキャッシュを保持する公開プロフィール専用エントリーポイントから行い、DB更新後の呼び出しと結果を確認する。入口のキャッシュ設定とブラウザー向けのHTTPキャッシュ制御を分けて確認する。

### Previewとアクセス制御

- [Worker Previews](https://developers.cloudflare.com/workers/previews/)を利用し、PRのpush後に`pnpm exec wrangler preview`でブランチのPreviewを更新する。2026-09-23の公式案内ではWrangler 4.135.0以降が必要となる。
- Previewごとにコード・画面とURLを切り替え、D1などのBindingsは共有可能とする。共有DBへの更新やschema変更は接続先の環境へ共通して反映されるため、動作確認する変更に応じて共有・分離を選ぶ。Preview名ごとのURLとデプロイを固定したURLをPRへ記載する。
- Basic認証を有効にしたテスト環境で、画面と表示に必要な静的ファイルの保護、OAuth往復、各エンドポイントの通常の認証・公開条件によるAPI呼出しを検証する。外部の相互リンク検証サービスによる取得テストは、そのサービスが到達できる検証用URLで行う。
- 外部OAuthのローカル・Preview往復にはOAuth Proxyプラグインを接続し、Providerに登録した安定したcallback URLと許可された戻り先を確認する。

### リクエスト制限と可観測性

- Web検証・一般APIのリクエスト制限をCloudflare WAFのRate Limitingルールへ設定する。認証endpointはBetter Auth標準のDB保存型Rate Limitを設定する。
- WAFの対象ホストとパス、カウント対象、閾値、期間、429応答を実環境で確認する。1時間のカウント期間は契約プランの対応を確認してから指定し、採用できる期間と回数を仕様へ反映する。[WAFのプラン別対応](https://developers.cloudflare.com/waf/rate-limiting-rules/)を確認する。
- Workers LogsとTracesを有効にし、`head_sampling_rate`で記録量を調整する。`console.log`・`console.warn`・`console.error`で重要度を分け、仕様で許可した項目を構造化JSONとして記録する。[Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)と[Traces](https://developers.cloudflare.com/workers/observability/traces/)を参照する。
- ソースマップで例外の元ファイルを追えること、秘密情報と利用者データの出力範囲が仕様どおりであることを確認する。

### Workers内の処理

- リクエストごとの状態はハンドラーのローカル変数・引数・Hono contextで渡し、`env`は環境のBindingsの参照に使う。
- 応答に必要な保存・検証は`await`または`return`で完了を待つ。応答後に実行できる処理は`ctx.waitUntil()`へ接続し、実行期限内に完了する単位にする。
- Better Authのバックグラウンド処理もWorkerの実行contextへ接続する。Vite Plusのlintに`typescript/no-floating-promises`を設定する。
- JSON出力などの大きなダウンロードを`TransformStream`で構築し、整形したJSONを逐次書き出す。読込側と書込側の完了・中断を処理する。
- トークンなどの乱数にはWeb Cryptoの`crypto.randomUUID()`・`crypto.getRandomValues()`を使用する。秘密値の検証は認証ライブラリの標準処理へ委ね、独自比較が必要な箇所では固定長化した値をタイミングに依存しないAPIで比較する。[Workersの実行ガイド](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)を参照する。

## 3. 認証と保存構造を接続する

- [テーブル構造の設計案](../specification/v0.1/main.ja.md#テーブル構造の設計案)から、採用設定でCLI生成したBetter Auth標準schemaとAccounts独自の6表を同じDrizzle schemaに組み合わせる。標準列は生成結果を正とし、公開`oauthClient.clientId`と内部`id`、`account.id`とProviderの`accountId`を区別する。
- Better Auth 1.7系の正式版と対応するDrizzle adapter・OAuth Providerを揃えて導入し、[1.7移行ガイド](https://better-auth.com/docs/guides/1-7-upgrade-guide)から採用版の設定を確認する。
- `better-auth/minimal`、暗号化、明示的なProvider連携、ログイン時更新、Cookie cache、DB joins、DB保存型Rate Limitを[認証ライブラリとの分担](../specification/v0.1/main.ja.md#認証ライブラリとの分担)に従って設定する。
- i18n、Last Login Method、multi-session、OAuth Proxy、Open APIを画面・APIへ接続する。TestUtilsは結合テストとE2Eの準備へ接続する。AdminプラグインはAccounts側で確定した運営権限へ対応付ける。
- Google・GitHub・ORCIDの実通信で共通ログインフロー、同一本人・Providerの複数アカウントの明示連携、元ユーザーでの解除後の再連携を検証する。`linkSocial()`・`unlinkAccount()`が標準schema上で期待通りに動作することと、state・nonce・PKCE、暗号化されたProvider tokenの保存を標準の認証経路で確認する。
- 初めての外部アカウントで標準のユーザー作成とログインが完了し、仮の表示名で利用を開始できることを確認する。表示名は標準のProviderマッピングなどで初期値を設定する。
- クライアント登録時に、Accountsのバックエンドが`client_credentials_scopes: ["identities:read"]`を設定し、`clientPrivileges`で必要な`configure-client-credentials-scopes`権限を与える。標準の登録APIへ接続する設定と、利用者の情報提供同意を区別する。[OAuth Provider](https://better-auth.com/docs/plugins/oauth-provider)に従って認可された範囲だけ登録できることを確認する。
- OAuth Providerの`consentPage`を「アカウント連携」画面へ接続する。今回の提供先と利用目的を表示し、外部アカウントの選択を既存の設定保存APIで保存した後、標準の`oauth2.consent`へ接続する。認可要求と保存先クライアントの対応はバックエンドで確認し、OAuth要求の検証とコード発行はBetter Authに委ねる。[標準の同意画面](https://better-auth.com/docs/plugins/oauth-provider#consent-screen)を参照する。
- 本人の提供先一覧と情報提供状態を、保存済みの同意・公開設定と現在の認可要求から組み立てる。初回選択、設定保存の失敗時、再連携時の保存済み選択を確認する。
- Client Credentialsの署名付きJWT、初回連携、scope・audience、公開鍵の登録・更新をAPIへ接続する。`private_key_jwt`とDPoPは公式OAuth Providerの設定・検証ヘルパーで構成し、利用側の標準ライブラリと接続して確認する。
- 標準の`rateLimit`表と採用プラグインのschemaを生成し、独自表のPK・FK・本人内UNIQUE・有効識別子の部分UNIQUE・検索索引をmigrationへ含める。認証用の標準表には採用版の実際の検索に必要な索引を確認する。生成したDrizzle relationsをadapterに渡し、同じ表間に複数の関連がある箇所は`relationName`を対応させる。
- 未検証URLの複数人登録、本人内150件、有効識別子の一意性、証明と複数識別子の対応、再検証失敗時の成功集合維持、Web識別子だけの移動、OAuth解除で他方式の証明が残る場合を保存層の検証対象にする。
- すべての日時をUTCとして保存し、Drizzle・Better Auth・JSON境界で単位とUTCの往復を確認する。
- 一覧・照合の読取条件と、公開設定保存・所有者移動・復元の一括書込を[読み取りと更新の単位](../specification/v0.1/main.ja.md#読み取りと更新の単位)に合わせる。D1の1文100バインド変数上限を守り、1操作の原子性が必要な書込は1回の`batch()`に収める。分割読取は元の入力順へ結果を戻す。

### D1のmigrationと運用コマンド

- Drizzle Kitでschema差分からmigration SQLを生成し、Wranglerが読むmigrationディレクトリに保存する。
- 独立したデータ移行SQLが必要な場合は`pnpm exec wrangler d1 migrations create <DATABASE> <MESSAGE>`で作成し、同じ履歴に含める。
- ローカルで`pnpm exec wrangler d1 migrations apply <DATABASE> --local`を実行し、stagingで`--remote --env staging`を指定して検証する。
- `pnpm exec wrangler d1 execute <DATABASE>`はSELECT、確認用SQL、シード、単発の保守処理に使い、実行環境を明示する。
- schema・索引変更後に`PRAGMA optimize`を実行する。[D1のSQL仕様](https://developers.cloudflare.com/d1/sql-api/sql-statements/#pragma-optimize)と[Wrangler D1コマンド](https://developers.cloudflare.com/workers/wrangler/commands/d1/)を参照する。
- 生成したmigrationをバージョン管理し、空DBと変更前schemaの双方から適用できることを確認する。

## 4. Accountsの機能を実装・移管する

- [URL検証仕様](../specification/v0.1/verify-url.ja.md)から、単一URL入力を起点とした未登録URLの受付、取得と証拠抽出、リンク検証が成立しない場合の同一要求内でのDNS TXT確認、結果の保存、保存済み識別情報による照合を実装する。両方法が不成立の場合も入力URLを未検証として保存する。移行元の既存テストを新しい条件へ対応付ける。
- セッション本人のプロフィールURLを期待値とし、入力URLの構文・取得先の安全性を検査してから公開ページを取得する。リンクが成立すればその成功結果を保存し、取得失敗・リンク不一致などで成立しなければ対象hostのDNS TXTを確認する。DNS成功時は`dns_txt`証明を入力URLと同じhostの登録済みURLに対応付ける。直近の方法別再検証結果と有効な証明・紐付けを分け、照合APIは保存済みの識別子・証明・現在の紐付け・公開許可で判定する。
- セッションから本人とプロフィールURLを決定し、正規化、HTML全体の許可リンク・可視テキスト、HTTP Link、サービス別の公開ページ解析を検証する。GitHubプロフィール・Gist、GitLab・Stack Overflow・Qiita・note・Zenn・Codeberg・X・Hugging Faceのプロフィール、Qiita・note・Zennの記事、Xの投稿、GitLabのMerge Request・Issue、Stack Overflowの質問・回答、Codebergのリポジトリ、Hugging Faceのモデル・データセット・Spacesに個別対応する。Reddit・KaggleのURLは汎用Webページとして登録・共通検証する。第三者投稿の読者コメントと`code`・`pre`内のコード例のURLも証拠候補に含め、異なるAccountsユーザーへのURLが併存する場合の判断不能を確認する。入力URLのリンク証明が成功した場合、URL規則で確定できる対象アカウントのプロフィールURL・ユーザー名を保存し、URLから確定できなければ取得済みの同一HTMLで対応を確認できた範囲だけ紐付ける。記事・投稿は作者、Codeberg・Hugging Faceの成果物は現在の所有アカウントを対象とし、組織名義も含める。所有アカウントとの対応を確認できなければ入力URL単独で検証する。403などの取得制限は判断不能とする。作者・所有者・識別子の判定をコメント内容から広げず、リンク検証の結果表示がページの編集権限を確認したように見えないことも確認する。
- [管理画面](../specification/v0.1/main.ja.md#管理画面と監査)の設定・アカウント連携・開発者向けへ機能を配置する。個別の公開先選択、一括指定、保存ボタンの状態、保存APIの検証を接続する。
- 公開プロフィールを未ログインで取得し、許可された情報と検証方法のバッジが初期HTMLに含まれることを確認する。
- 公開プロフィールの初回取得でD1からHTMLを生成し、再取得ではWorkers Cacheから返すことを確認する。外部リンク0件でも表示名・固定IDを返し、退会後は404となることを確認する。公開設定・外部アカウント解除・所有者変更・退会によるDB更新後は、対象プロフィールのpurgeと次の取得での公開内容の再評価を確認する。
- OAuthクライアント管理を接続し、登録件数上限、提供先としての表示、Client ID・公開鍵、登録情報の編集・削除を仕様からテストする。
- [Accounts API](../specification/v0.1/main.ja.md#accounts-api)の入力・出力スキーマ、HTTPメソッド、認証・認可、不正な入力を含む場合の400応答を実装する。
- Valibotの共通スキーマを公式`@valibot/to-json-schema`で変換し、OpenAPI 3.2.1の`query`操作・認証・応答定義へ組み込む。開発者向け画面でQUERYに対応する表示UIを使い、表示と送信を確認する。Better AuthのOpen APIプラグインが出力する認証APIとAccountsの資源APIを区別して案内する。[ValibotのJSON Schema変換](https://valibot.dev/guides/json-schema/)、[HonoのQUERY対応](https://github.com/honojs/hono/releases/tag/v4.13.0)を参照する。
- [JSONによるバックアップと移行](../specification/v0.1/main.ja.md#jsonによるバックアップと移行)から、出力前の内容確認・復元ボタン・設定反映・登録候補を実装する。存在しないクライアントIDを含む公開設定も確定した保存方式で取り込む。
- [退会](../specification/v0.1/main.ja.md#accountsユーザーの退会)を、標準の認証削除とAccounts独自データの削除へ接続する。

### OSSライセンス画面

- 単体テストはValibotスキーマ、URL処理、権限判定、機能フックを中心にVitestで作成する。利用者の操作・認可・保存・情報提供に必要な振る舞いを期待値とし、内部構造や文言などの細部は変更に追従できる形で扱う。

- Markdownの相対リンク、仕様・計画・実装・OpenAPIの参照関係を検査し、確定した契約を利用側文書へ接続する。

### READMEに追加する手順

1. リポジトリで`pnpm install`を実行する。
2. Accountsのディレクトリで`pnpm exec wrangler login`を実行する。
3. `pnpm exec wrangler d1 create <DATABASE_NAME>`で環境用DBを作成する。
4. `wrangler.jsonc`の名前・DB ID・Bindings・環境設定を実際の値へ合わせる。
5. `.env.example`からローカル環境を用意し、デプロイ先へ`pnpm exec wrangler secret put <NAME> --env staging`で秘密値を登録する。
6. migrationを適用し、Bindings型を生成する。
7. 通常の画面開発はVite Plusの開発scriptで起動する。Worker単体の確認には`pnpm exec wrangler dev --env staging`を使い、遠隔の実行環境を確認する場合は対象環境を指定して`--remote`で起動する。
8. 型検査・lint・単体・Workers結合テストとビルドを実行し、ローカルpreviewで成果物を確認する。
9. `pnpm exec wrangler preview`でPRのPreviewを更新し、Basic認証とOAuth設定を含めて利用フローを確認する。
