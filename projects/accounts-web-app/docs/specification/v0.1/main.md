## 説明

- あらゆるアカウントのIDを統合して管理できるサービス
- v0.1は個人名義のAccountsユーザーを対象とする

## 存在意義・独立したサービスにする理由

1. 無料主義の貢献度アップロードのアカウント管理を簡単にする
   - サービスの実装側・利用側の両方で、利用を簡単にしたい
2. アカウント統合の処理はとても複雑なので、責務の分離の為に切り出す
3. 他の無料主義サービスが、同じ内容を実装する必要がない状態にしたい
4. ポイント管理サービス以外からでも使用できると思う
5.  `points`サービスが、複数のサービスから、自分が登録した`accounts`サービスを選べるようにする

## 責務

- Accountsは、Accounts内のユーザーと証明済みの外部アカウントの対応を管理する
- Pointsは、貢献データとポイントを管理する
- 貢献データはPointsへアップロードし、PointsがAccounts APIへ貢献者の照合を依頼する
- Accountsは、貢献内容やポイント情報を保存しない

## Pointsなどの連携サービスとの境界

- AccountsとPointsなどの連携サービスは、それぞれ独立したサービスとしてユーザー、ログイン手段、セッションを管理する
- 利用者は連携先サービスへログインした後、Accountsとの情報連携を開始し、Accounts側で認証して情報提供に同意する
- AccountsのOAuth Providerは、外部アカウントの情報提供と貢献者照合の権限を連携先へ付与する
- サブドメインや運営者にかかわらず、連携先を独立したOAuthクライアントとして扱う
- PointsのGoogle・GitHubログイン、重要操作の再認証、管理者判定はPointsの責務とする
- PointsユーザーIDとAccountsユーザーIDは、それぞれのサービスが管理する識別子とする。両者を情報連携で対応付ける具体的なルールは未決事項で定める
- Pointsは、CSV取込、FIX、未受領分の受領、ポイント台帳・残高、パッケージ、経済履歴とそれらの公開設定を管理する
- PointsがMarketsなどに提供する経済情報・操作権限のOAuth資源APIは、Pointsが管理する
- Accountsは外部アカウントの現在の紐付けと公開許可を管理し、Pointsは照合結果を使って貢献の帰属を決定する
- 外部アカウントの追加・解除・紐付け先変更・公開設定変更後も、Pointsで確定済みの貢献・ポイントの帰属を維持する

## 利用開始の流れ

- Accountsで登録し、外部アカウントを連携した後、Pointsなどのサービスへ連携できる
- PointsなどのサービスからAccountsへの連携を開始し、Accountsへの登録、外部アカウントの連携、公開対象の選択を行える
- どちらの入口からも、一通りの設定を完了できる

## v0.1で実装する機能

1. Accountsユーザーのプロフィール
   - プロフィール項目は、表示名・AccountsユーザーIDとする
   - ユーザーは、自分のAccountsプロフィールの表示名を設定できる
   - 外部アカウントは、表示名や識別情報で見分けられるようにする
   - Accountsと外部アカウントのプロフィールで扱う情報は、表示名や識別情報などのテキスト情報とする
   - `accounts.freeism.app`内のユーザーIDを、公開された固定IDとして表示する
   - 誰でも、公開されたAccountsユーザーIDを貢献データの貢献者として指定できる
   - 誰でも閲覧できる公開プロフィールページを設ける
   - 公開プロフィールURLは、`https://accounts.freeism.app/profiles/{accountsUserId}`とする
   - 公開プロフィールは、GitHubなどの外部アカウントとAccountsユーザーIDの対応を表示することを主な用途とする
   - ユーザーは、公開プロフィールに掲載する連携アカウントを個別に選択できる
2. 貢献者の識別
   - 貢献データでは、次のいずれかで貢献者を指定できる
     1. 外部サービスのプロフィールURL
     2. Accounts内のユーザーID
     3. 外部サービス名と、そのサービスにおけるアカウントの固有IDの組み合わせ
   - プロフィールURL、または外部サービス名と固有IDが指定された場合は、証明済みの外部アカウントと照合する
   - Accounts APIは、指定された外部アカウントに紐付き、問い合わせ元のOAuthクライアントへの公開が許可されたAccountsユーザーを返す
   - 1つの外部アカウントを指定した照合結果は、該当するAccountsユーザー1件、または該当なしとする
   - OAuthクライアントは、本人が事前に公開を許可した外部アカウントを、本人の操作中以外にも照合できる
   - Pointsは、第三者による貢献データのアップロード時やバックグラウンド処理時にも、許可済みの外部アカウントからAccountsユーザーを照合できる
   - 照合時点で有効な、問い合わせ元のOAuthクライアントへの公開許可を確認する
3. Accountsへの登録・ログイン
   - v0.1では、Google OAuthとGitHub OAuthをログイン手段にする
   - ログアウト状態で、Accountsユーザーに紐付いていないGoogle・GitHubアカウントを認証した場合は、新規登録の確認画面を表示する
   - 確認画面でAccountsの表示名を設定し、「新規登録」を実行すると、Accountsユーザーを作成して認証済みの外部アカウントを紐付ける
   - 確認画面には、既存のログイン手段でAccountsへログインし、設定画面から外部アカウントを追加連携する導線も設ける
   - 紐付け済みのGoogle・GitHubアカウントでAccountsへログインできる
   - 後から追加したGoogle・GitHubアカウントでも、紐付け先のAccountsユーザーへログインできる
   - 通常の設定画面では、各AccountsユーザーにGoogle・GitHubアカウントを合計で最低1件残し、最後のログイン手段の連携解除を許可しない
   - GitHubアカウントが残っていれば最後のGoogleアカウントを解除でき、Googleアカウントが残っていれば最後のGitHubアカウントを解除できる
4. 外部アカウントの所有権証明
   - 1つのAccountsユーザーへ、Google・GitHubそれぞれ複数の外部アカウントを紐付けられる
   - Google・GitHubの連携アカウント数に上限を設けない
   - 各外部アカウントの紐付け先は、Accountsユーザー1件に限定する
   - この一意性の制約は、Google OAuth・GitHub OAuth・Webページのリンク検証のすべてに適用する
   - 同じ外部プロフィールURLやOAuthアカウントの紐付け先は、常に1つのAccountsユーザーとする
   - 紐付け先のない外部アカウントは、所有権の証明が成功した時点で、そのAccountsユーザーへ即時に紐付ける
   - 別のAccountsユーザーに紐付け済みの場合は、元のAccountsユーザーでの連携解除が必要であることを案内する
   - 紐付け先を変更する場合は、元のAccountsユーザーで連携を解除した後、移動先のAccountsユーザーで所有権を改めて証明して連携する
   - 元のAccountsユーザーには、Google・GitHubのログイン手段を合計で最低1件残す
   - Google OAuth・GitHub OAuth・Webページのリンク検証のいずれも、紐付けの追加によって、すでにPointsへ帰属した貢献データやポイントは変更しない
   1. Google OAuth
      - ログインに使用したGoogleアカウントに加えて、別のGoogleアカウントもOAuthで所有を証明して紐付けられる
      - Googleアカウントの紐付けには、Googleの固有IDを使用する
      - 本人の管理画面では、取得できる表示名・メールアドレス・固有IDを扱い、複数のGoogleアカウントを見分けられるようにする
      - 一般公開・OAuthクライアントへの提供項目は、取得できる表示名と固有IDとする
   2. GitHub OAuth
      - GitHub OAuthで所有を証明して紐付けられる
      - GitHubの固有IDを外部アカウントの識別子として使用する
      - 所有権証明には必要最小限の権限を要求し、ユーザー名やメールアドレスが異なる場合も固有IDに基づいて同じ外部アカウントを識別する
   3. Webページのリンクによる所有権証明
      - 本人が編集でき、Accountsの公開プロフィールへのリンクを確認できる公開Webページを、サービスを限定せず対象とする
      - 本人がAccountsの設定画面で外部ページのURLを登録し、その外部ページに自分のAccounts公開プロフィールへのリンクを設置する
      - Web URLは、1つのAccountsユーザーにつき最大30件登録できる
      - 本人が検証を実行すると、Accountsのバックエンドが外部ページを取得し、リンク先が自分のAccounts公開プロフィールURLと正規化後に完全一致することを確認する
      - 検証が成功した外部ページを、そのAccountsユーザーへ紐付ける
      - 外部ページを公開プロフィールに掲載するかは、一般公開の設定に従う
      - 証明用リンクをたどると、外部ページとAccountsユーザーIDの対応を確認できる
      - 証明後の紐付けは、本人がAccountsで解除するまで有効とする
      - 所有権の検証は紐付けの登録時に行い、所有関係は現在の紐付けとして管理する
5. OAuth Provider
   - v0.1の連携対象は、Pointsのようなバックエンドを持つWebサービスとする
   - `points.freeism.app`から権限付与できるようにする
   - 今後は、複数の`accounts.freeism.app`のようなサービスから、どれかを選べるようにしたいのでOAuth Providerにする
   - v0.1から、外部サービスの開発者がAccountsの画面で自分のアプリをOAuthクライアントとして登録できる
   - 登録したアプリにはClient IDとClient Secretを発行する
   - 登録したアプリは、登録者のAccountsユーザーが管理し、アプリ設定の変更とアプリ自体の削除を行える
   - 登録アプリの管理者は、Accountsの画面でClient IDとClient Secretを管理できる
6. 閲覧権限の制御
   - Accounts APIを通じて提供する外部アカウントの公開範囲は、OAuthクライアントごとに管理する
   - 公開先は、一般公開と各OAuthクライアントをそれぞれ独立して設定する
   - 公開対象の選択単位は外部アカウントとし、そのアカウントについてあらかじめ定めた表示名・識別情報などの項目をまとめて提供する
   - 一般公開する連携アカウントも、OAuthクライアントへの公開と同様に、ユーザーが明示的に選択する
   - Google OAuth・GitHub OAuth・Webページのリンク検証のいずれで証明した外部アカウントにも、同じ公開範囲の制御を適用する
   - Webページのリンクによる所有権証明と、証明済みWebプロフィールを各OAuthクライアントへ提供する許可は、独立して管理する
   - Web上で公開されている証明用リンク自体の閲覧範囲は、Accounts APIの閲覧権限とは別に扱う
   - OAuthクライアントへ初めて権限を付与するときは、すべての外部アカウントを非公開にする
   - ユーザーが同意画面で選択した外部アカウントだけを、そのOAuthクライアントへ公開する
   - 後から追加した外部アカウントは、ユーザーが明示的に公開するまで既存のOAuthクライアントへ公開しない
   - 公開された外部アカウントに限り、そのOAuthクライアントはプロフィールURL、または外部サービス名と固有IDからAccountsユーザーを照合できる
   - ユーザーは、OAuthクライアントに対する外部アカウントの公開を後から解除できる
   - 公開を解除した外部アカウントは、それ以後の照合結果に含めない
   - 公開解除前にPointsへ帰属した貢献データやポイントは変更しない
7. ドメインは、`accounts.freeism.app`
   - 一旦は、freeism向けに提供したいため
   - [https://accounts.freeism.app/](https://accounts.freeism.app/)
8. データ移行を簡単にしたい
   - 同じAccountsユーザーの設定をバックアップし、復元できるようにする
   - 別の運営者や本人が運営するAccounts互換サービスへ、登録情報をエクスポートして取り込めるようにする
   - インポート・エクスポートのファイル形式はJSONとする
   - 別のAccounts互換サービスへ移行した外部アカウントは、移行先で所有権を改めて証明した後に紐付けを有効にする
   - 詳細は[JSONによるバックアップと移行](#jsonによるバックアップと移行)に従う
9. OSSとしてすべてを公開

## 外部識別情報の仕様

### URL正規化

外部ページの登録、貢献者照合、証明用リンクの判定に、共通のURL正規化規則を適用する。

- schemeとhostを小文字化し、国際化ドメインをASCII/Punycode表現に統一する
- HTTPSのURLを受け付け、default portとfragmentを除去する
- 空のpathを`/`に統一する
- サービス固有の明示規則がないqueryは保持する
- 末尾slash、`/about`などのpath、subdomainはそれぞれのURLの意味に従って区別する
- percent encodingは、同じoctetを表す安全な範囲で正規化する
- 外部URLの受付と取得先の制約は、[外部ページの取得](#外部ページの取得)に従う
- URLによる一致判定には正規化後の完全一致を使用し、サービス名と固有IDによる識別にはその組み合わせの一致を使用する

### GitHubプロフィールURLの解決

- `https://github.com/{login}`形式の1階層の利用者プロフィールURLを、GitHub REST APIの`GET /users/{username}`で固有IDへ解決する
- 利用者type、数値ID、`html_url`と入力URLの正規化後の一致を検証する
- 外部サービス名は`github`、固有IDは数値IDの10進文字列とし、解決した時点の情報として扱う
- ユーザー名の変更後も同じ固有IDを識別する。ユーザー名が別アカウントへ再利用された場合は、その時点の固有IDを識別する
- URLから固有IDへの解決は要求ごとに外部APIで行い、その要求内で得た結果を照合の根拠とする
- 外部サービスの固有IDの解決と、証明済み外部アカウントからAccountsユーザーへの照合を分ける。Accountsユーザーの提供には問い合わせ元への公開許可を適用する
- 外部APIの404、429、timeout、5xx、応答schema不正による解決失敗と、固有IDへの解決に成功したうえでAccountsユーザーが該当しない結果を区別する。解決失敗は失敗として返し、連携先はAPI契約に従って再試行や利用者への案内を行う
- API呼び出しはバックエンドで実行する。OAuth AppのClient ID・Client SecretをWorker Secretで管理し、Basic認証と固定したAPI versionヘッダーを付ける
- 同じ処理内の正規化済みURLを重複排除し、1回の一括解決は最大1,000種類、最大6並列、1件の期限は3秒、全体の期限は120秒とする。全体期限に達したら残りのfetchを中断する
- アプリ全体で共有するD1のAPI予算から、必要な呼び出し件数を原子的に事前予約する。応答の`X-RateLimit-Remaining`と`X-RateLimit-Reset`で予算を補正する
- 必要な予算を確保できない場合は、外部APIの呼び出しを始める前に一括要求全体を`429 GITHUB_IDENTITY_LOOKUP_RATE_LIMITED`とし、安全に算出した`Retry-After`を返す
- 解決結果として保存する情報は、外部サービス名、固有ID、正規化プロフィールURL、解決日時とする

### 外部認証情報

- 外部サービスの認証情報はバックエンドで管理し、保存するOAuth tokenはアプリケーション層で暗号化する
- OAuth tokenの暗号化にはBetter Auth標準の`account.encryptOAuthTokens`とversioned secretsを使用する。環境別のWorker Secretで管理し、先頭のcurrent secretで新規保存し、残りの旧secretは復号に使用する
- Token refresh・再連携などの次回保存でcurrent versionへ更新する。復号では未知versionと改ざんを拒否する
- browserへ渡すプロフィール・セッション情報と、外部サービスの秘密情報を分離する
- 所有権証明に使う情報と、一般公開・OAuthクライアントに提供する情報を区別する
- 外部アカウントの追加連携は、本人の操作と外部サービスでの認証に基づいて行う
- 同じ外部アカウントかどうかは外部サービス名と固有IDで判定し、メールアドレスが異なる場合も本人による明示的な追加連携を許可する
- 追加連携後も、本人が設定したAccountsの表示名を維持する
- GitHubの連携解除では、GitHub側のtoken失効が成功したか、すでに失効済みであることを確認してから、保存したAccess Token・Refresh Tokenを削除して紐付けを解除する

## Webページの検証仕様

### 証明に使用するリンク

- 登録された外部ページをAccountsのバックエンドが取得する
- HTMLの`a[href]`・`link[href]`とHTTPの`Link`ヘッダーを、リンクの候補とする
- `rel`のtokenに`me`を持つリンクがある場合は、そのリンクを証明候補とする。それ以外のページでは、通常の許可されたリンクを候補とする
- 候補のリンク先を正規化し、検証する本人のAccounts公開プロフィールURLと完全一致した場合に証明を成立させる
- 取得したHTMLの実際のリンク要素とHTTPヘッダーを証拠の範囲とし、本文、code block、comment、JSON、画像alt、JavaScriptが生成するDOM、iframe内の記述は証明候補から除外する
- 本人による検証操作で条件を満たした場合に自動承認する

### 外部ページの取得

- 取得先はHTTPS・port 443の公開Webページとする
- userinfo付きURL、IP literal、localhost、private・link-local・loopback・reserved hostname/address、Cloud metadata addressを受付・取得対象から除外する
- Cloudflare Workersでは、入力時のhost検査と`global_fetch_strictly_public`による公開Internet向けの接続制約を組み合わせる
- redirectは最大3回まで手動で追跡し、各遷移先に同じscheme・port・userinfo・hostの検査を適用する
- 各取得は`cache: no-store`相当でcacheをbypassし、新しく取得した応答を証拠とする。staleな応答や`Age`などcache由来を示す応答は検証失敗として扱う
- 全体の取得期限は5秒、response上限は1MiBとし、`text/html`または`text/plain`を受け付ける
- 取得要求には外部ページの検証に必要なヘッダーだけを付け、利用者のCookie、Authorization、client IP、内部ヘッダーは転送対象から除外する
- HTMLとHTTPヘッダーの静的な解析で検証し、JavaScriptの実行とsubresourceの取得は検証処理の対象から除外する

### 検証要求の制御

- Web検証は、Accountsユーザーと正規化URLの組み合わせごとに5回/時、Accountsユーザー全体で30回/日を初期上限とする
- 同じ操作の冪等な再送は保存済みの結果を返し、同じ副作用に対する頻度制限を重ねて消費しない
- 上限値は429の発生、誤検知、不正利用の観測に基づいて変更し、設定変更をレビューする
- 短時間の大量検証、連続失敗、明らかなbot、異常なIP・ASN、頻度上限への接近などのリスクに応じてTurnstileを要求する
- TurnstileのSite Key、Secret、再使用検知用の保存領域は、Accountsの環境ごとに管理する
- challengeが必要な場合は`428 TURNSTILE_REQUIRED`と、その環境のSite Key・Accountsの検証操作に対応する固定actionを返す。画面はtokenを取得し、同じ操作を1回再送する
- AccountsのバックエンドでSiteverifyを実行し、期待するhostname・action、5分の有効期限、一回限りの使用を検査する。検証に成功した要求だけを後続処理へ進める
- 本人認証、操作の認可、再認証、頻度制限、冪等性、所有権のリンク検証は、それぞれの条件を満たす必要がある。WAFによるchallengeとアプリのTurnstileは独立して扱う
- 本人向けWeb検証APIの成功・失敗応答には、`Cache-Control: no-store`と`Pragma: no-cache`を付ける

## 操作の認可と再認証

- 外部アカウントの追加・解除・再連携、Web所有権の確定、公開範囲の拡大、OAuthクライアント・Client Secret・署名鍵の変更には、15分以内のAccountsでの本人再認証を要求する
- 再認証した外部サービスの固有IDが、操作中のAccountsユーザーに紐付くことをバックエンドで確認する。成功後はセッションIDを更新する
- 公開範囲の縮小だけを行う変更は、通常の本人認証で実行できる。複数の変更をまとめた要求に公開範囲の拡大が含まれる場合は、要求全体へ再認証を適用する
- 操作ごとの認証・認可・再認証条件をバックエンドの共通ポリシーで管理し、対象操作へ一貫して適用する
- Google・GitHubそれぞれで直近の本人再認証を確認する具体的な方式は、未決事項で定める

## 管理画面と監査

- 本人が、外部アカウントの追加連携、外部URLの登録、検証実行、検証結果の確認、連携解除、公開先の設定を行える
- 本人向けの外部アカウント一覧では、外部サービス名、取得できる表示名、固有ID・URLなどの識別情報、連携日時、検証方法・検証日時・検証結果を確認できる
- 公開を許可したGitHubアカウントの提供項目は、取得できる表示名、外部サービス名と固有ID、プロフィールURL、検証状態、連携日時とする
- 公開を許可したWebページの提供項目は、確認済みURL、検証方法、検証日時とする
- 上記の提供項目を、一般公開プロフィールとOAuthクライアントへの提供に共通して適用する。検証失敗の詳細は本人向け画面で確認できる
- Webページへ設置する証明用のAccounts公開プロフィールURLを表示し、コピーできるようにする
- UIは日本語と英語を提供する。初期言語は、ブラウザが日本語の場合に日本語、それ以外の場合に英語とする
- 読み込み中、登録がない状態、成功、失敗を画面で判別できるようにする
- 状態や失敗理由はテキストで示し、確認操作・エラー・通知をキーボードとスクリーンリーダーで判別できるようにする
- 外部サービスの表示名やURLは、表示時に適切にエスケープする
- 編集と検証の権限は、Accountsのバックエンドが本人の認証状態に基づいて確認する
- 所有権確認の開始・成功・失敗、検証方法、外部URLの安全な表現、最終URL、content hash、検証日時、失敗理由を監査対象とする
- ログイン・外部連携の成功と拒否、連携解除・再連携、再認証、公開許可の変更、OAuthクライアント・Client Secret・署名鍵の変更、refresh失敗、token種別・scopeによる拒否を監査対象とする
- 監査情報は追記型で保存し、OAuth token、認証code、Cookie、Client Secret、外部HTML本文、外部APIの応答本文、メールアドレスは監査の保存・ログ出力対象から除外する
- 一般公開とOAuthクライアントへ提供する項目は、それぞれ確定した提供項目に従う

## JSONによるバックアップと移行

- 本人のプロフィール・設定と、外部アカウントの安全なmetadataをJSONで出力する。バックエンドで対象のAccountsユーザーと各データへの権限を確認する
- 外部アカウントのmetadataは、外部サービス名、固有ID・URL、表示名、連携日時、検証方法・検証日時・検証結果など、本人が管理画面で確認できる情報を対象とする
- OAuth token、セッション、Client Secret、暗号鍵、URL検証HTML本文は出力対象から除外する
- timestampはUTCのRFC 3339、IDは不変文字列として出力する。認証付きexport応答には`Cache-Control: private, no-store`を付ける
- 出力前に対象情報、件数の見込み、非公開情報を含むかを本人に示す。出力操作では紐付け・検証日時・設定などの保存状態を維持する
- 別のAccounts互換サービスへの取込では、外部アカウントの登録情報を再証明のための入力として扱う。移行先でGoogle・GitHubのOAuthまたはWebページのリンク検証を行い、所有権と紐付けの一意性を確認してから有効にする
- Webページの再証明では、移行先のAccounts公開プロフィールURLをリンク先として検証する
- JSONの詳細schema、同じAccountsユーザーへの復元、固定IDや公開許可などの引き継ぎ範囲は、未決事項で定める

## 受け入れ条件

- 未連携のGoogle・GitHubで認証すると、表示名を設定する新規登録確認へ進み、本人の確定操作でAccountsユーザーを作成できる
- 複数の外部アカウントを追加でき、各外部アカウントの紐付け先は同時点で最大1ユーザーとなる
- 同じ外部アカウントへの連携処理が競合しても一意性を維持する。メールアドレスが同じだけでは紐付けを成立させず、異なるメールアドレスの明示連携は成立し、Accountsの設定済み表示名を維持する
- 元のユーザーにログイン手段を残して連携を解除し、別のAccountsユーザーで再証明して紐付けられる
- 登録した外部ページに本人の公開プロフィールへの適切なリンクがあれば検証に成功し、別のAccountsユーザーへのリンクや本文中のURL文字列だけでは成立しない
- URL正規化の同値・非同値、`rel=me`の優先、通常リンク、HTTP Link、取得先・redirect・容量・時間・MIME・cacheの制約を判定できる
- Web URLは30件まで登録でき、31件目を拒否する。userinfo、各redirect先のprivate到達、DNS rebinding相当のprivate接続、redirect loopを拒否し、Cookie・Authorization・client IP・内部ヘッダーを転送しない
- Web検証の回数上限と冪等な再送、Turnstileのhostname・action不一致、期限切れ・再使用、同一操作の再送、成功・失敗応答のcache制御を検証できる
- 一般公開プロフィールへの掲載を選ばずに所有権を証明でき、一般公開と各クライアントへの公開対象を独立して変更できる
- Googleのメールアドレスは本人の管理画面で見分けに使え、公開・クライアント提供では確定した表示名と固有IDを扱う
- URLまたは外部サービス名と固有IDから、照合時点で公開を許可されたAccountsユーザーを最大1件返す
- GitHubユーザー名の変更・再利用、利用者type・固有ID・URLの不正、外部APIの404・429・timeout・5xxを区別でき、API解決失敗を正常な照合結果として扱わない
- 別々の要求の間にGitHubユーザー名が再利用された場合、後の要求は外部APIを再実行して変更後の固有IDを返す
- GitHub URLの重複排除、1,000種類の境界、最大6並列、期限での中断、API予算予約の競合・不足・応答による補正を検証できる
- 保存tokenの暗号化とbrowser・セッション応答・ログへの平文非露出を確認でき、GitHubの連携解除は外部tokenの失効確認と保存tokenの削除を経て完了する
- 暗号化secretの更新後も保持中の旧versionを復号でき、新規保存・refresh・再連携でcurrent versionへ更新される。未知version・改ざんは拒否する
- 本人だけが設定・検証・exportを実行でき、重要操作は再認証の期限と主体の条件を満たした場合に成立する
- 許可済みクライアントによる照合は本人の操作中以外にも成立し、公開解除後はその外部アカウントが照合結果から外れる
- PointsとAccountsでそれぞれ独立したログイン状態を保ちながら、本人の同意による情報連携が成立する
- JSONでのバックアップ・復元と別Accounts互換サービスへの移行が、確定する引き継ぎ範囲に従って成立する
- 別Accounts互換サービスへ取り込んだ外部アカウントは、移行先で再証明した後に有効になり、元のJSONの検証結果だけでは所有権を確定しない
- JSON出力は本人の権限内のmetadataに限定され、秘密情報を含まず、元の保存状態を変更しない
- 日本語・英語の初期選択、読み込み中・空・成功・失敗の表示、キーボードとスクリーンリーダーによる操作を確認できる
- 紐付け・公開設定の変更後も、Pointsの確定済み貢献・ポイントの帰属が維持される

## 未決事項

- OAuthクライアント自身が照合APIを利用するための認証方式と権限を具体化する
- GitHub APIの固定versionヘッダーの値と、単件・一括照合APIの入出力schemaを具体化する
- Googleの連携解除時に行う、外部サービス側のtoken失効と保存tokenの削除条件を定める
- Accountsの重要操作に必要な15分以内の本人再認証について、Google・GitHubそれぞれで成立を確認する方式を定める
- PointsユーザーとAccountsユーザーの対応件数、連携先の変更・解除・各サービスの退会時の扱いを定める

- JSONの詳細schema、固定ID・公開許可・登録OAuthクライアントの引き継ぎ、同じAccountsユーザーへの復元時の所有権証明の扱いと既存設定との統合方法を定める

- AccountsのWeb検証で使用するTurnstileの固定action名を定める
- 外部サービスから取得した表示名などを更新するタイミングを定める
