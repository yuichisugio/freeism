## この実装の目的

- Accountsによって、IDを統合的に管理したい
- 囲い込みがなく、管理者に依存せず、無料のサービス

## 問題点

## 詳細
改訂内容：全データの完全コピーを廃止し、保存先別の選択データと編集アプリ別の権限を採用する。  
文書の位置付け：設計・実装計画。ここで要求するアクセス制御・同期処理・受け入れテストは、実装済み・試験済みという意味ではない。外部仕様の記述と、Accountsが追加する設計要件を区別する。

**採用する要件**

Accountsの通常の画面表示、検索、設定変更、業務APIはCloudflare D1だけを利用する。D1を正本とし、AT Protocol SpacesとSolidは外部同期にだけ使用する。v0.1はD1のみで実装し、v0.2で同期機能を追加する。

Accountsは、利用者がAT Protocol Spaces向けに選んだデータだけをSpacesへ、Solid向けに選んだデータだけをPodへ保存する。両方の選択内容は同一でなくてよい。Accountsは、選択されたデータを必ずアクセス制御下に置き、一般公開する機能や公開保存へのフォールバックを実装しない。

Accountsは、全データの本人用完全コピーを別途作らない。非公開であっても、未選択データを外部へ送らない。保存対象を選ぶ操作と、編集アプリへアクセスを許可する操作は分離する。

外部保存先は、利用者が許可した編集アプリに対し、そのアプリへ許可したデータと操作だけを認める。Accountsの画面を経由しないAPIアクセスでも、同じ制限が効くことを対応条件とする。単に「本人としてログインした」「有効なトークンを持っている」だけで、保存済みの全データを読める設計にはしない。

外部変更の取り込みは、同期ボタンによる取得、検証、競合確認、本人の承認を経てからD1へ反映する。未知項目は原本として保持するが、その保持を理由に未選択情報を別の保存先やアプリへ渡さない。

| 項目 | 改訂後の方針 |
| --- | --- |
| アプリの通常処理・正本 | D1のみ |
| 外部保存先 | 対応するAT Protocol Spaces／Solid Pod |
| 外部保存対象 | 保存先ごとに本人が明示選択した項目だけ |
| 全データの完全コピー | 作らない |
| 一般公開 | 行わない。公開モードへの切り替えも提供しない |
| 外部編集アプリ | 本人が許可したアプリだけ |
| アプリの取得範囲 | 保存対象と、そのアプリへの許可範囲の共通部分 |
| 読み取りと編集 | 別々に管理する。初期値は許可なし |
| 外部変更の反映 | 同期ボタン → 検証・差分・競合確認 → 承認 → D1 |
| 仕様・保存先の機能不足 | 非公開性・権限を緩めず、該当連携を未対応として停止 |

**以前の計画から廃止・変更する事項**

以前の「本人用の全データ完全コピー＋共有用データ」という2層構成は廃止する。「D1にしかない情報は一切ない」「外部だけで全ユーザーデータを復元できる」という保証も廃止する。

改訂後は、未選択データがD1だけに存在することを意図した動作とする。外部からの再利用・復元は、その保存先に同期済みで、かつ取得するアプリに許可された範囲だけを対象とする。部分データしか取得できないことを「欠損」や「削除」と解釈しない。

公開されたユーザーデータを生成しない方針は、一般公開されている元のSNSプロフィールURLを、選択された値として非公開保存することまで禁止する意味ではない。Accountsが外部に作るコピーの公開範囲を制限する。

DIDの解決情報、アプリのOAuthメタデータ、公開鍵、スキーマ定義など、プロトコルの接続・検証に必要な公開情報はユーザーデータ本文とは区別する。Accountsはそれらに個人プロフィール、SNS関連付け一覧、選択した項目一覧、非公開リソースの目録を埋め込まない。公開メタデータも含めて一切何も公開しないことは、本計画の保証ではない。AT ProtocolのOAuthは公開クライアントメタデータを使用する。[^at-oauth]

**保証する範囲と信頼の境界**

「非公開」は、不特定多数や未許可の利用者・アプリがデータを取得できないというアクセス制御を意味する。保存先の運営者にも内容を読めないことや、エンドツーエンド暗号化を意味しない。Spacesの公式案内もアクセス制御と暗号化による機密性を区別している。[^spaces-alpha]

許可したアプリがすでに受け取ったデータのコピーや、そのアプリ側のD1に取り込んだ情報を、権限取消だけで回収・消去できるとは保証しない。将来の取得を止めることと、過去のコピーの削除は分離する。

利用者本人が保存先の管理画面から意図的に別の権限へ変更することや、保存先運営者が管理権限で介入することまで、クライアントであるAccountsが絶対に阻止できるとはしない。保証は、選定した保存先がアクセス制御を正しく実施し、管理用権限が外部編集アプリへ渡されていない条件下で成立する。Accountsは外部権限の不一致を検知した場合、同期を停止し、修復または再承認を求める。

共有設定の正本はD1に置くが、外部で実際に有効な権限とは区別する。Accountsは、未反映の希望設定を「保護済み」と表示しない。

**保存対象とアプリ権限のモデル**

保存先を `p`、編集アプリを `a` とし、次の集合を管理する。実装ではデータIDとフィールドIDの組、必要な操作、ポリシー版で表す。

```text
S(p)    = 本人が、その保存先への保存を許可したデータ
R(p,a)  = 本人が、その編集アプリによる読み取りを許可したデータ
W(p,a)  = 本人が、その編集アプリによる編集を許可したデータ

外部保存するデータ            = D1からS(p)だけを抽出したデータ
編集アプリが読み取れるデータ  = S(p) ∩ R(p,a)
編集アプリが変更できるデータ  = S(p) ∩ W(p,a)
```

これはAccountsの設計ルールであり、任意のPDS・Podが自動的にこの集合演算を実装するという意味ではない。同期Adapterが外部の保存単位と認可方式へ変換し、保存先による強制を試験する。

認証済み主体、検証済みアプリ識別子、対象領域、許可操作、有効なトークンまたはgrant、保存先ポリシーがすべて整合するときだけアクセスを許可する。OAuthで広い権限が発行されても、保存先のアプリ別・対象別の制限を迂回できないことを合格条件とする。

保存先ごとの初期選択は空とする。新しい設定項目やSNSアカウントをD1へ追加しても、自動的に外部保存・アプリ共有へ追加しない。カテゴリ全体を選ぶ操作は、初期実装ではその時点の具体的な項目へ展開する。将来の追加項目まで許可する設定はv0.2の既定動作に含めない。

読み取り、更新、追加、削除、アクセス権の管理を区別する。一般の編集アプリへ権限管理を渡さない。「編集を許可」の既定対象は、明示したデータの読み取りと更新とし、追加・削除は別の承認がある場合だけ有効にする。外部が操作を細分化できない場合は、実際に付与される操作を表示して承認を求める。要求した制限を守れない場合は、その権限設定を未対応とする。

**具体例**

以下は説明用の設定であり、固定の機能要件ではない。

| D1のデータ | Spacesへ非公開保存 | Solidへ非公開保存 |
| --- | --- | --- |
| 表示名 | する | する |
| GitHubアカウント | する | しない |
| 通知設定 | しない | する |
| 連絡先メールアドレス | しない | しない |

利用者が編集アプリBにSpaces上の表示名だけの閲覧を許可し、編集アプリCにSpaces上のGitHub情報だけの閲覧・更新を許可した場合、BはGitHub情報を取得できず、Cは表示名を取得できない。どちらも、D1にだけある連絡先メールアドレスを外部保存先から取得できない。

BとCが同じ利用者のDIDで認証されていても、BとCの権限を同一にしない。Solid側の許可をSpaces側へ、Spaces側の許可をSolid側へ自動転用しない。

**外部の保存単位と権限の分離**

Accountsは、許可範囲の異なるデータを、外部サーバーが区別して認可できる単位へ分ける。v0.2では、原則として「保存先×許可する編集アプリ×操作セット」ごとに領域を分け、同じ領域には同じ許可範囲のデータだけを入れる。安全性と競合処理が確認できた後に、同じ権限を持つ領域の統合を検討してよい。

```text
D1：正本。全ユーザーデータを管理する
  │
  ├─ Spaces：アプリB用の非公開領域
  │    └─ Bに許可した表示名だけ
  │
  ├─ Spaces：アプリC用の非公開領域
  │    └─ Cに許可したGitHub情報だけ
  │
  └─ Solid：アプリD用の非公開リソース群
       └─ Dに許可した設定だけ
```

外部保存を選んだが、まだ編集アプリへ許可していないデータは、保存対象の選択分だけを含む管理用の非公開領域へ保存してよい。この領域は全データバックアップではなく、他アプリに一括アクセスさせる対象にもならない。後からアプリへ一部だけ許可するときは、選択内容を抽出した別の権限領域を作る。

同じ設定を複数のアプリ別領域に保存する場合、外部に複数のコピーができる。Accountsは各コピーの対応関係と前回合意済みの版をD1に保持する。外部の複数コピーが違う値に変更された場合は、手動同期で競合として扱う。

1つの文書に「閲覧のみの項目」と「更新可能な項目」を混ぜ、文書全体への書き込み権限を渡さない。外部サーバーがフィールド単位の認可を保証しない場合、文書またはSpaceを分ける。表示制御やクライアント側のフィルタリングを認可の代用にしない。

**AT Protocol Spacesへの対応条件**

Spacesはalphaのままv0.2の実装対象にする。通常の公開リポジトリーへの保存経路は作らない。利用者が選んだデータを権限境界ごとのSpaceへ入れ、非公開設定とアプリ制限を設定できた先だけを利用する。

確認した仕様案では、Space全体の `read` は読み取り境界内の全体を対象とし、`read_self` は本人のレコードに限定する別の権限である。また、`simplespace` の `appAccess` には検証したアプリ識別子に基づく許可リストが定義されている。これらは採用版での動作確認が必要な仕様案である。[^spaces-proposal]

Adapterは、非公開のユーザー許可条件とアプリ許可リストを明示設定する。公開ユーザーポリシーや全アプリ許可を、設定省略によって選ばない。具体的なフィールド名・型・既定値は採用するalpha版のLexiconと実装に合わせる。

特に、Space credentialの発行経路だけでなく、本人のPDSに対するOAuthの直接読み取り、`read_self`、一覧取得、レポジトリー取得、blob取得など、採用版の全読み取り経路を確認する。許可リストが1つの経路にだけ効き、別経路から未許可アプリが読める場合は要件未達とする。

アプリの許可には検証された識別子を使う。アプリが送信した名前や任意の `client_id` を、そのまま信用しない。必要なアプリ認証・署名を提供できないクライアントは、厳密なアプリ制限の対応対象にしない。バックエンドを持つアプリ構成が必要になる場合があるが、採用版で確認して決定する。

要求scopeは対象Space・コレクション・操作を可能な限り明示し、包括権限や管理権限を一般の編集アプリに要求しない。省略値や将来のスキーマ追加によって権限が広がらないかも試験する。

許可リストとOAuth直接アクセスの整合性は、この文書の作成時点では実行試験していない。必要な制約を強制できないPDSでは、その連携を有効化しない。Spacesを使う方針を維持しつつ、必要に応じて対応版の採用・サーバー側への修正を行う。D1の業務層は変更しない。

公式alpha案内は、破壊的変更、データ消去、セキュリティレビュー未完了、機微情報を投入しないことを明示している。計画はalpha対応を含めるが、試験は合成データで行う。実ユーザーの機微データを守れることを、alphaの存在だけから保証しない。[^spaces-alpha]

**Solidへの対応条件**

Solidでは、選択データだけを非公開リソースへ保存する。利用者を表すWebIDの検証だけでなく、その利用者が使う編集アプリの識別子も確認したうえで、対象リソースと操作を制限する。

ACPは、主体・クライアント・対象などを条件にするモデルを定義する。Inrupt ESSにもWebIDとClient IDを組み合わせるアクセス方針が文書化されている。これらを対応候補とするが、ACP対応という表示だけで要件達成とは判断しない。[^acp][^ess-identity]

Adapterは、本人のWebIDと許可アプリのClient IDが同時に一致する条件を採用する。クライアント制限のない広い所有者許可、親から継承される許可、別のgrantなどで制限を迂回できないことを確認する。外部編集アプリへACL／ACRの管理権限や、Pod全体の包括権限を渡さない。

WACでリソースを非公開にすることと、アプリ別の強い識別・権限制限を実現することは区別する。`Origin` やCORSだけに依存した制限を、サーバーからの直接アクセスを含むアプリ認可として扱わない。[^wac]

Access Requests／Grantsを利用する場合も、アプリに発行するgrantとリソース側の許可範囲を一致させる。ESSの説明では、リソースの方針とgrantの許可の共通部分が有効になる。コンテナーの子への継承も確認する。[^ess-grants]

未許可アプリが本人のWebIDでログインしただけで全部読める、または一般の編集アプリが権限を書き換えられるPodは、本計画の対応対象にしない。必要な制限がない場合に「読み取り専用にすればよい」とも扱わない。読み取り自体の漏出を止める必要がある。

**外部データの発見と別アプリへの許可**

別の対応Accounts系アプリは、自分自身のClient IDで接続し、本人の承認を受けた領域だけを発見・取得する。元のAccountsのトークン、アプリ鍵、管理権限を流用しない。

保存場所の案内、manifest、データIDの一覧にも、本文と整合する非公開権限を適用する。SolidのType Index等を使う場合は、非公開の目録または承認済みの接続案内を利用する。非公開文書の所在や内容分類を、公開プロフィールへ丸ごと載せない。Type Indexには公開・非公開の区別がある。[^type-index]

別アプリが広い読み取り権限を要求した場合、本人の認証だけで承認済みとしない。Accountsで設定した上限を変更する場合は、対象データと相手アプリを示した独立した明示承認を必要とする。トークン発行画面だけで外部リソースの制約を迂回できる構成は採用しない。

別アプリによる取得許可と、そのアプリのD1へ正式に取り込む承認は別にする。別アプリは選択データを候補として取得し、検証・競合確認後に自分のD1へ反映する。

元のAccountsが停止しても、本人が保存先の管理機能または対応する別の管理アプリから、選択データへの許可を付け直せることを相互運用の目標とする。これは本人による新しい管理判断であり、未許可アプリに自動的に権限が渡ることではない。外部未保存のD1専用データを復元できるとはしない。

**共通データ形式・メタデータ**

D1のテーブル構造とは別に、選択データを表すポータブル形式を定義する。外部文書は常に部分データとして扱い、`coverage = selected` を基本とする。`coverage = full` を使った全件コピーは生成しない。

外部文書には、スキーマ版、共有領域内の安定ID、対象範囲、値の型、選択済みの値、同期に必要な版情報を含める。D1の全設定一覧、未選択の項目名や件数、内部アカウントID、内部認証情報を便宜的に添付しない。

複数領域を横断する共通識別子は必要性を検討し、不要な追跡可能性を増やさない。内部の `dataset_id` と外部の領域別IDを分離できる構成にする。同じデータを複数先へ出力した対応関係はD1に保持する。

未設定、null、false、0、空文字列、空配列を区別する。AT ProtocolとSolidに変換するときも、選択値の意味と型を失わない。配列要素の選択には安定IDを使う。

証明や添付が複数の属性を含む場合、1属性の選択を理由に原本全体を送らない。必要な実体・参照先・含まれる情報をプレビューし、本人の承認範囲内でだけ送る。署名を壊す任意の部分削除を「部分証明」として扱わない。安全な部分提示に対応できない場合は、その共有方法を未対応とする。

汎用の添付取得URL、blob、履歴、変更通知、ダウンロードAPIにも同じ許可境界を適用する。本文だけ保護され、添付や一覧から未許可の内容を取得できる実装は認めない。アプリ別の権限が異なるblobを、公開リンクや無制限の共有URLで使い回さない。

**v0.1で準備する設計**

v0.1はD1だけで通常機能を実装する。外部SDKや同期UIはまだ組み込まないが、後から範囲選択を追加するため、次の基礎を設ける。

| 基礎 | 実装内容 |
| --- | --- |
| 安定ID | アカウント、SNS情報、設定、証明、配列要素の識別子 |
| フィールド台帳 | 型、未設定の意味、外部保存可否、選択粒度、依存する添付や証明 |
| デフォルト拒否 | 新項目は未選択。自動的に外部保存対象にしない |
| 版管理 | データ形式の版、D1の更新番号、選択設定の版 |
| 削除記録 | 削除と未取得・未選択を区別する |
| 更新経路 | 通常編集と将来の取り込みが同じ検証済み更新処理を通る |
| 選択抽出 | 指定したデータID・フィールドだけを出す純粋な変換処理 |
| 原本と評価 | 外部証明の原本と、Accountsが行う検証結果を分離する |

変換テストでは、選択データが欠落しないことに加え、未選択データが絶対に混入しないことを確認する。新しい項目を追加しても、既存の選択やアプリ許可が広がらないことを確認する。

**D1の論理テーブル構成**

以下は責務の分離案であり、実際のテーブル名・数は既存設計に合わせて調整する。

Accountsは、保存先ごとの選択とアプリ別grantを独立して管理する。外部原本や任意のJSONに書かれたアカウントID・Client IDを、内部の所有関係・権限の根拠にしない。

D1の更新とOutbox登録は同じ成功条件で実行する。D1の `batch()` はSQLのトランザクションを提供するが、外部通信はその対象外である。[^d1-batch]

同期実行はWorkersのScheduled HandlerとD1のOutboxで構成できる。別の永続ストレージは必須にしない。[^cron]

**初回接続のフロー**

```text
本人がAccountsへログイン
  → 外部アカウントを接続し、DID／WebIDと正当な認証元を検証
  → 保存先ごとに外部保存したいデータを選択
  → 送信予定の値・添付・メタデータを確認
  → 必要な非公開領域と権限を作成・確認
  → 編集アプリを許可する場合はアプリ・対象・操作を別途承認
  → 既存の外部データがある場合は候補として検証・比較
  → 選択データだけを送信
  → 非公開性・アプリ制限・保存結果を確認して同期完了
```

接続しただけではデータを送らない。Accountsは、空の領域の権限を先に設定するか、作成時から非公開が保証される方式を使う。「データをいったん公開で作成し、後からACLを締める」手順を採用しない。

新しいデータが継承する親コンテナーの権限、追加したblobの権限、管理用領域の初期値も確認する。安全な初期化ができない保存先では、機微な実データの作成を開始しない。

**Accountsで編集した場合：D1から外部へ**

```text
通常の編集
  → 検証してD1へ保存
  → 選択対象に該当する変更だけをOutboxへ記録
  → Workerが現在の選択版・アプリ許可版・外部権限を確認
  → その権限領域に許可された項目だけを生成
  → 外部版を条件として保存
  → 成功した保存先・領域・D1版だけを同期済みにする
```

未選択データを編集しても、外部へ送信しない。同期処理は送信直前にも選択設定を再確認し、保存対象から外れた値を古いジョブが再送しないようにする。

外部が前回合意済み版から変更されている場合、その領域への自動上書きを停止する。外部内容をD1の正本へ自動採用せず、手動同期を待つ。認可ポリシーの照合や送信結果の確認は、自動取り込みとは区別する。

同じ項目を複数のアプリ別領域へ保存する場合も、ある領域の外部編集を別領域へ直接横流ししない。D1への手動承認を経た後に、各領域の現在の許可範囲へ再出力する。

**同期ボタン：外部からD1へ**

```text
同期ボタン
  → 本人が取得対象の保存先・許可領域を選ぶ
  → D1の更新番号と現在の選択・許可版を記録
  → 許可対象だけを取得し、候補・原本としてD1へ保存
  → 主体・アプリ・出所・形式・値・証明を検証
  → 前回合意済み値／現在のD1／今回の外部値を比較
  → 差分と競合を表示
  → 本人が採用内容を承認
  → 選択・権限・D1版を再確認して正式反映
  → 必要な範囲だけの外部送信予定を作成
```

外部が任意の追加フィールドを含んでいても、未許可のD1項目や別アカウントの情報を更新できないようにする。追加フィールドは原本・未対応データとして扱い、D1へ新たに採用して外部共有する場合は別途確認する。

外部の `verified: true`、管理者フラグ、共有先のClient ID、公開設定を、そのまま権限や検証結果へ昇格させない。外部文書を書けるアプリに、Accountsの選択設定や他アプリの権限を変更する能力を与えない。

読み取りだけを許可したアプリによる外部書き込みが発見された場合は、単なる競合ではなく認可設定の異常として扱う。D1へは自動反映しない。

**競合・削除・同期状態**

前回合意済み状態をB、D1の選択対象をL、外部候補をRとして、保存先・アプリ領域ごとに3方向比較を行う。同じ項目がLとRの両方で異なる値になった場合は、本人が選択する。更新日時や処理順だけで勝者を決めない。

保存対象から外れたこと、アプリの権限がなくなったこと、外部リソースが削除されたこと、403／404／取得失敗を区別する。これらをD1の項目削除へ自動変換しない。

通常のAT ProtocolリポジトリーのAPIをSpacesにそのまま流用できるとは仮定しない。採用するSpaces版とSolid実装で、安全な条件付き更新の手段を検証する。Solidでは対応するETag／条件付き更新等を利用する。[^solid-protocol]

同期済みの判定は、選択対象のD1版、選択設定版、アプリ権限版、外部の実際の適用状態を使う。未選択データは「未同期」ではなく「外部保存対象外」と表示する。

D1保存と外部保存の間には遅延や失敗があり得る。「選択した最新データが常に外部にある」という保証はしない。外部から利用できるのは、同期が完了した版である。

**未知項目の保持と非公開性を両立する**

Accountsは外部の原本をD1に保持し、未知フィールドを既知のDTOへの変換で捨てない。未知項目のJSONネスト、RDFの述語・データ型等を安全に往復できない場合は、切り捨てて保存せず書き込みを停止する。

未知項目の保持は「元の権限領域で、他アプリの情報を勝手に消さない」ためのものである。未知項目を、未選択でも外部へ新規出力してよいという意味ではない。

新規保存、新規のアプリ許可、保存先追加では、D1から選択済み項目だけを抽出する。未知項目を含む原本全体を、新しいアプリへの共有データとして再利用しない。原本と同じ範囲へ書き戻す場合だけ、既存の未知項目をその範囲内で保持する。

未知項目を含む既存文書の許可範囲を縮める必要がある場合、文書から未知項目を勝手に削除する代わりに、古い領域へのアプリ権限を取り消し、選択項目だけを含む別の非公開領域を作る。元の未知データの保管・削除は、本人の意図と所有範囲を確認して別操作で扱う。

本人が未知拡張そのものの転送を明示選択する機能を将来追加する場合は、その拡張が丸ごとの転送単位になることと、内容をAccountsが解釈できないことを示す。v0.2で未知拡張を自動共有しない。

**選択解除・アプリ取消・権限変更**

| 操作 | D1 | 外部側の処理 |
| --- | --- | --- |
| 保存先の選択から項目を外す | 正本は残す | 新規送信停止、古い外部コピー・添付・履歴等を権限境界に沿って削除または到達不能化 |
| 特定アプリの許可を取り消す | 正本・保存対象は維持 | 当該アプリのgrant／認可経路を失効・拒否。ほかのアプリの許可を巻き込まない |
| アプリの読める項目を減らす | 正本は維持 | 旧領域への許可を制限し、必要なら選択済み項目だけの新領域へ切り替える |
| 閲覧のみへ変更する | 正本は維持 | 対象アプリの書き込み権限を取り消す |
| 外部接続を解除する | 正本は維持 | 同期停止、接続トークン破棄。外部データの削除・残置を本人に確認 |
| Accounts内でデータを削除する | 削除記録を残す | 同期対象の該当コピーについて削除を処理する |

権限変更では、変更前のOutboxを無効化し、進行中または結果不明の送信も照合する。新しい権限を適用・確認するまでは、漏出のおそれがある領域へ新データを送らない。

保存先が停止中の場合や、既発行credentialが期限まで有効な場合は、取消が完了したとは表示しない。「停止要求済み」「外部反映待ち」「実効確認済み」を分ける。短命credential、失効方式、既存トークンによる再取得可否を採用実装ごとに試験する。

保存先が保持するバックアップ、受信アプリのコピー、既取得内容の記憶まで物理消去できるとは保証しない。通常の取得APIからの将来アクセス制限と、サービス運営者によるデータ消去範囲は区別する。

**認証・内部アカウントとの関連付け**

Accountsへのログインと外部同期先への接続を分離する。同期トークンが失効しても、D1の通常機能は使える状態を維持する。

AT Protocolでは、OAuthで取得したDID、DID文書が指すPDS、そのPDSが指す認可サーバー、認可応答・トークン応答の対応を検証する。PKCEやDPoP等は採用仕様に従う。DIDと認可サーバーの独立した対応確認は、公式OAuth仕様に規定される。[^at-oauth]

Solidでは、署名、issuer、audience、有効期限等と、WebIDプロファイルが認める認証元を確認する。対象WebIDで認証されていることと、Pod・アプリに必要な権限があることは別に判定する。[^solid-oidc]

外部ID、取得したリソースの所有者、編集したアプリ、D1の内部アカウントを分けて追跡する。メールアドレスや自己申告のID一致だけで別アカウントを統合しない。

トークン、秘密鍵、セッション、パスワードハッシュ、内部管理権限は選択可能な同期項目に含めない。ユーザー由来URLの取得では接続先・リダイレクト・応答サイズを検証し、想定外のoriginへ認証情報を転送しない。

**実装順序**

| 段階 | 実装・検証内容 |
| --- | --- |
| 事前検証 | 合成データでアプリ別拒否、対象別拒否、全読み取り経路、認証元検証、初期化時の非公開性を確認 |
| v0.1 | D1通常機能、安定ID、フィールド台帳、デフォルト拒否、選択抽出、更新・削除管理を実装 |
| v0.2・同期基盤 | 選択設定、アプリ別grant、権限領域、Outbox、候補、差分・競合・承認を実装 |
| v0.2・外部接続 | 対応版を固定したSpaces／Solid Adapter、実効権限確認、取消、再接続を実装 |
| 既存データ移行 | 外部の選択は全件未選択から開始。本人が選んだ内容だけ初回同期 |
| 相互運用試験 | 別アプリが許可範囲だけを読み、外部編集が承認後にD1へ反映されることを確認 |

最初から本体へ外部プロトコルを導入する必要はない。ただし、本要件で最も影響が大きいのは「接続先がアプリ別の上限を全経路で強制できるか」であり、この事前検証はv0.1の設計確定前に行う。

既存の全件コピーが実環境に存在する場合は、コピー・権限・添付・旧世代を棚卸しし、本人に対象を示して旧grantと不要コピーを整理する。新形式への移行で、古い全件コピーが読み取り可能なまま残らないようにする。旧コピーを無断で破壊的に削除する自動移行は行わない。

既存データからの初回同期は、現在のD1から選択部分だけを生成する。過去のすべての編集を外部へ再送しない。途中でD1版や選択版が変わった場合は、再計算または後続の送信として扱う。

**完了条件とUI表示**

v0.1の完了条件は、D1だけで通常機能が動き、選択項目を欠落なく取り出せ、未選択項目の混入をテストで検出できることとする。

v0.2の完了条件は、採用したSpacesとSolidの各実装に対し、非公開保存、保存先別選択、アプリ別の範囲制限、手動取り込み、競合検出、未知項目保持、取消、部分データの相互運用を試験済みであることとする。alphaやACPの名称だけで対応済みと表示しない。

UIには保存先ごとの選択項目、各アプリの閲覧・更新範囲、外部の実効権限、同期済みの版を表示する。「外部保存対象外」「送信待ち」「外部変更あり」「競合」「許可反映待ち」「取消反映待ち」「認可方式未対応」を区別する。

**最終方針：AccountsはD1を正本にし、本人が保存先ごとに選んだデータだけを非公開で同期する。外部保存したことは全アプリへの許可を意味せず、許可アプリごとに対象データと操作を外部でも制限する。全件コピー・一般公開・包括ログインによる全件閲覧は採用しない。**
