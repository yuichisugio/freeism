# Markets Web App v0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `markets.freeism.app` を商材情報を含む Auction だけを担う独立した Cloudflare Workers アプリとして空の D1 から構築し、Google 認証、Points 明示連携、multi-unit uniform-price Auction、Hibernate WebSocket、全 winner 原子精算、proof／review／履歴 UI を承認済み v0.2 仕様どおり提供する。

**Architecture:** 親計画が作る TanStack Start の静的SPA shell + 4固定route prerender、Hono、Workers Static Assets の上へ、Markets 専用 Better Auth／Drizzle D1、Auction ごとの `AuctionRoom` Durable Object、D1 outbox を正本とする `AuctionSettlementWorkflow` を追加する。browser mutation は同一 origin Hono API から `AuctionRoom` へ送り、WebSocket は購読専用にする。Points とは `POINTS_SERVICE` Service Binding を transport にし、`points-worker` 所有 OpenAPIから生成した clientと、grant／scopeを分離したOAuth bearer tokenだけで連携する。

**Tech Stack:** Node `24.18.0`、pnpm `10.33.3`、Vite Plus `0.2.4`、TanStack Start `1.168.27`、React `19.2.7`、Hono `4.12.28`、Better Auth `1.7.0-rc.1`（開発・staging限定）、Drizzle ORM `0.45.2`、Drizzle Kit `0.31.10`、Cloudflare Workers／Static Assets／D1／Durable Objects／Workflows、Wrangler `4.108.0`、Vitest `4.1.10`、Workers Vitest pool `0.18.2`、`@playwright/test` `1.61.1`。

- price／quantity／sequence／versionはD1 `INTEGER`とJavaScript safe integerを使う。小数JSON number、D1 `REAL`、client時刻によるorderingを経済計算へ使用しない。Points component vectorをMarketsで正本化せず、settlementでは`pointPackageRevisionId`、`priceTicks`、`quantity`をPointsへ渡す（DEC-109、DEC-131、DEC-167）。
- CSV 1行からAuction 1件と最初の不変Auction revision 1件を作成する。UTF-8、5MiB、1,000非空行、server再parse、server draftなし、全件成功または0件、`Idempotency-Key`＋canonical payload hashを守る（DEC-114、DEC-115、DEC-118、DEC-129、DEC-225、DEC-262）。

- `END_OF_AUCTION`終了処理だけが同じcutoff snapshotから再計算する。確定的な残高不足者だけを1回blacklistし、一時障害で候補を除外しない。`BUY_NOW`は要求した1 buyer／全数量だけを対象にし、失敗者除外、代替winner、clearing再計算へ絶対に入れない。全winner・全axis captureはPointsの1 D1 transactionへ1requestで送り、capture後にrelease、refund、別winner再計算を行わない（DEC-144、DEC-164〜DEC-173、DEC-264）。
- `END_OF_AUCTION`のcapture前Points残高再検査で不足した場合は、M2M Problem Detailsの`insufficientReservationIds`をcurrent roundへ照合し、該当userだけを除外、旧ACTIVE reservationを全releaseし、同じcutoffから再計算する。`BUY_NOW`は外部作用前、決定的reservation拒否でID 0件、または全reservation未capture＋ACTIVE分release完了の3種evidenceだけで、代替者を選ばずhold全数量を一度だけ`FAILED_RESTORED`へ進める。結果不明はholdを維持してmanual action、capture済みは`CAPTURED_PENDING_FINALIZE`からproofへforward finalizeする。IDはbrowser／public response／logへ出さない。0 tick winnerは0 vector reservationを`ACTIVE -> CAPTURED`へ進め、receiptを残すがledger／残高を変更しない。
- 通常successは`{ data, meta }`、errorはRFC 9457 `application/problem+json`＋安定した`SCREAMING_SNAKE_CASE` codeとする。private responseは`Cache-Control: private, no-store`、immutable public proofはcontent hash付きpublic cacheとする（DEC-158、DEC-197）。
