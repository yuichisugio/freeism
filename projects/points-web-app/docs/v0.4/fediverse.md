**PointsのFediverse化・相互運用設計のまとめ**

整理日：2026-09-21。対象は、これまでの議論で最後に採用した方針である。過去に検討した案と最終方針を区別し、未決定の詳細を実装済み・合意済みとして扱わない。

**この設計の中心は、「本人の紐づけはAccounts A、投稿権限は評価グループのオーナー、評価内容は各評価グループが責任を持つ」という分担である。**

Pointsは、全グループ共通の「客観的に正しい貢献」を判定するサービスにはしない。Pointsは、正当なグループが登録した評価を、Accounts Aの証明に基づいて正しいDIDへ紐づける。そのデータを、許可された範囲で複数のPointsサービスから利用できるようにする。

ここでいうFediverse化は、ActivityPubを採用するという決定ではない。今回の構想は、AT Protocol SpacesやSolidによるデータの交換・共有と、複数アプリによる再利用を中心にしている。各Pointsがすべて同じ評価を採用することや、一つの共有DBを共同運営することは前提にしない。

**登場する主体と責任を分ける。**

| 主体 | この設計での責任 |
| --- | --- |
| 利用者 | データの外部保存先・保存対象・利用を許可するアプリを選ぶ |
| Accounts A | SNSアカウントとDIDの対応を検証し、署名付きVCを発行する |
| 他のAccounts・編集アプリ | 許可されたデータを表示・編集する。独自の自己申告をAccounts Aの証明として扱わない |
| 評価グループのオーナー | そのグループに貢献評価を登録できる主体を指定する |
| 投稿権限を持つ人・サービス | グループの責任で貢献内容・評価値を登録する |
| 各Pointsサービス | VC・投稿権限・データの対応を検証し、採用する評価をDIDに帰属させる |
| PDS・Solidサーバー | 選択された外部データを保存し、対応するアクセス制御と読み書きを提供する |

評価グループは「誰がどの基準で評価するか」の単位であり、Pointsサービスは「データを処理・提供するアプリ」の単位である。両者は概念として分ける。1サービスが何グループを扱うかなどの具体的な対応関係は、まだ固定していない。

**本人の紐づけには、Accounts Aの有効なVCだけを採用する。**

Pointsは、任意のAccountsサービスが保存した `verified: true` や、サービス名・URLの自己申告を、本人性の証明として受け入れない。現在の信頼対象はAccounts Aであり、別の発行者を自動的に追加しない。

Accounts Aが証明する対象は、次の組である。これは意味を説明する例であり、正式なVCのJSON形式ではない。

```text
発行者：Accounts A
対象DID：did:example:alice
SNS：GitHub
SNS側のアカウント識別子：123456
確認日時・有効性に関する情報：……
Accounts Aの署名：上記の対応関係を保護する
```

Pointsは、信頼したAccounts Aに結び付く鍵、署名、対象DID、SNS側の識別子、形式、有効期間・失効状態を受理ルールに従って検証する。署名対象の外にある編集可能な値で、付与先を上書きしない。データ署名は改ざん検出に利用できるが、発行者の主張の真実性は署名だけで保証されない。[1][2]

Pointsは、証明を提出した人ではなく、証明が対象としているDIDへ評価を帰属させる。投稿者と貢献者が別人である場合も認める。VCの保有者と証明の対象は、必ずしも同一ではない。[1]

他の編集アプリが、本人の許可を得てAccounts Aの既存VCを運ぶことは可能にする。「証明の発行者としてAを信頼すること」と「編集アプリをAだけに限定すること」は別である。ただし、既存VCを別アプリが変更・再発行しても、その新しい証明をAの証明としては認めない。

Pointsは、Accounts Aが行ったSNSの本人確認を、各SNSのOAuth等で再実行することを必須にしない。これは、初期の「すべてのPointsが自分でSNSを再検証する」案から整理した方針である。

Accounts Aが誤った紐づけへ署名することや、Aの鍵が侵害されることは、この信頼前提の破綻として残る。現段階は、本人性の判断まで完全に非中央集権化した構成ではない。

**紐づけVCと、貢献の投稿権限は独立して検証する。**

Accounts AのVCは「SNSアカウントとDIDの対応」を証明する。VCを持っているだけで、任意の評価グループへ投稿できることにはしない。VC Data Modelも、それ単独で完全な認可フレームワークを提供するものではない。[1]

評価グループGの正当なオーナーが投稿者Rを指定し、Pointsはその指定を確認する。投稿者が本文に `authorized: true` や任意のオーナー名を書くだけでは通過させない。正当なグループ管理情報と、認証または署名で確認できる投稿主体を照合する。

複数のPointsが同じ権限を検証できるようにする必要はあるが、所有者署名付きの権限文書、管理API、グループ用識別子などのどれを採用するかは未決定である。外部レコードに自己申告された権限を信用しないことだけを確定条件とする。

通常データを編集できるアプリへ、グループのオーナー情報、投稿者の許可一覧、他アプリの権限、Accounts Aの発行機能を自由に変更する権限は渡さない。

**評価内容の真偽と評価値は、各評価グループの責任にする。**

例えば、グループGの権限者が「GitHubの123456番に対して貢献度100を認定する」と登録した場合、Pointsは投稿権限を確認し、Accounts AのVCから対応するDIDを取得する。

Pointsはこの記録を「グループGはAliceを100と評価した」と扱う。freeism共通の仕組みは、その活動が実際に行われたか、その評価が客観的に100に値するかを再審査しない。

| Pointsが必須にする保証 | Points共通の仕組みでは保証しないこと |
| --- | --- |
| SNSとDIDの対応についてAccounts Aの証明がある | 権限者がいつも事実に即した評価をする |
| 対象グループが許可した主体による登録である | すべてのグループが同じ評価基準を使う |
| 他グループ・他のDIDへの偽装や改ざんを受け入れない | 評価値が全利用者にとって公正である |

利用者や利用サービスは、どのグループの評価を採用するかを選ぶ。虚偽・恣意的な評価をするグループは信用を失い得るが、人気低下はプロトコルが自動保証する罰則ではない。そのリスクをグループ運営と利用者の選択に委ねることを、意図した方針として採用する。

不正の扱いも区別する。Accounts Aを装った証明や、投稿権限のない登録は拒否する。一方、権限者が行った好ましくない評価は、本人性や権限の偽装と同一視せず、そのグループを採用するかという判断で扱う。

**正常な登録から貢献度の帰属までの流れは、次のようになる。**

```text
本人
  → Accounts AでSNSアカウントとDIDの対応を確認する
  → Accounts Aが紐づけVCを発行する

評価グループのオーナー
  → 投稿者Rへ、そのグループの投稿権限を与える

投稿者R
  → グループID・対象SNSアカウント・評価内容を登録する

Points
  → Rの投稿権限を確認する
  → Accounts AのVCを検証する
  → 貢献データのSNS識別子とVC内のSNS識別子を照合する
  → VCの対象DIDへ、グループの評価として帰属させる
  → 同じ登録の再送・再同期による重複反映を防ぐ
```

他人のVCをコピーしても、提出者自身のDIDへ付け替えることは認めない。貢献データのDIDとVCの対象DIDが食い違う場合は拒否する。評価グループを変更して、別グループが行った評価として見せることも認めない。

本人の確認クリックで、署名不正や投稿権限不足を無視する経路は作らない。一方、正当な権限者による評価内容を承認するために、共通の追加審査やオーナーの毎回の再承認を必須にはしない。

**外部保存は、指定したデータだけの非公開同期とする。**

以前の「全データを非公開で外部へ完全コピーする」案は採用しない。利用者はSpacesへ保存する項目と、Solidへ保存する項目を別々に選ぶ。未選択の情報は外部へ送らない。

データを外部へ保存する許可と、他の編集アプリへ閲覧・編集を許すことも分ける。アプリBが読める範囲は、「その保存先への保存対象」と「Bへ閲覧を許可した対象」の共通部分だけとする。

同じ本人のDID／WebIDで認証できても、すべての非公開データを読める設計にはしない。閲覧、編集、権限管理を区別し、データの取得・変更範囲を外部サーバーでも強制する。権限が異なるデータは、外部が分離して認可できる領域に分ける。ACPにはクライアントを条件とするモデルがあるが、その対応表示だけで全経路の制約が実現済みとは判断しない。[3]

検証用VCや権限証明も、選択・許可の対象として扱う。Pointsが必要な証明を取得できない場合は、該当データの採用を保留する。証明不足を解決するために、共有範囲を勝手に広げない。複数の属性を含むVCを、1項目の共有操作に便乗して丸ごと送らない。

共有されたサービス名・URLは、編集用の登録候補である。Pointsが本人性の根拠として利用するには、別途Accounts AのVCが必要になる。「URL一覧を共有すること」と「確認済みであることを共有すること」を区別する。

この方針は、SNS一覧、貢献評価、VC、判定結果等のユーザーデータを一般公開しないという意味である。接続や検証に必要な公開鍵・アプリ情報等まで、すべて非公開にすることは要求していない。

権限取消は将来の取得を止めるために使う。既に取得したアプリのコピーまで、取消操作で自動消去できるとは扱わない。また、外部保存先の運営者にも読めない暗号化を、この非公開設定だけで保証するものではない。Spacesはアクセス制御と暗号化による機密性を区別している。[4]

**D1を中心に動かし、外部プロトコルは同期の境界へ置く。**

これまで、D1正本・v0.1内部実装・v0.2外部同期という段階計画は、主にAccountsについて確定している。Pointsにも同じ方針を適用する構成案は次のとおりである。Pointsの詳細なリリース範囲まで、既に確定したとは扱わない。

```text
Accounts／Pointsの通常処理
           ↓
       各サービスのD1
           ↕
      同期・検証の処理
           ↕
  許可されたSpaces／Solidのデータ
           ↕
  別の対応サービスの同期・検証処理
           ↕
       別サービスの内部DB
```

通常の表示、検索、設定、貢献度処理は、そのサービスのDBに確定した状態を利用する。外部へは選択された変更だけを反映する。外部で変更された内容は、同期ボタンで取得し、証明・権限の検証、差分・競合確認、承認を経てDBへ取り込む。

他アプリの変更を無言で上書きしない。未知項目は元の原本と権限範囲を保持するが、その保持を理由に別のアプリや保存先へ未許可データを転送しない。見えない項目・未選択項目・取得失敗を、項目削除として扱わない。

D1保存と外部同期完了は区別する。未選択データと、まだ外部へ同期できていない最新変更は、D1だけに存在する場合がある。したがって、全データの復元や、すべてのサービスが常に同じ値を持つことは保証しない。

「D1を正本にする」は各サービスが自分の正式状態を持つという意味であり、freeismの1つのD1が他のすべてのPointsの判断まで決定するという意味ではない。他の実装にD1の採用を強制せず、共有形式・権限・証明の検証で相互運用する。

**不正データの排除は、共通の必須検証と、追加の判定共有に分ける。**

最優先は、各Pointsが無効なVC・権限不足・対象不一致を正式な表示や集計へ採用しないことである。悪意あるデータを外部に保存できたこと自体を、正当性の根拠にしない。

AT Protocolのラベルは、対象URI、判定者、対象の特定の版などに結び付いた判断を共有する補助として使える。ラベルが付くまで不正データを受理する方式にはしない。[5]

Spacesの非公開データについては、公開ラベル配信へ判定を流さない。仕様案は、ラベルを対象と同じ非公開境界のレコードとして保存する方法を示している。[6]

Solidでは、検証・除外の結果を独立した非公開リソースとして表現する。これはfreeism側で定義するアプリケーションの仕組みであり、Solidが自動的に貢献評価を審査するという意味ではない。通常の書き込み権限と、ACLを変更する権限は分けられる。[7]

| 操作 | この設計での扱い |
| --- | --- |
| 取り込み・集計からの除外 | 各Pointsが自分のDB・出力に対して行う |
| 書き込みの拒否・権限取消 | その登録経路・保存先の権限管理で強制する |
| 保存済みデータの削除 | 自分が削除権限を持つ範囲で行う |
| 他者のPDSやDBからの完全消去 | 通常の除外・ラベルで実現できるとはしない |

Spacesは、各ユーザーのPDS上にあるデータをアプリが集めるモデルである。Spaceの管理と、各参加者の保存データの管理は同一ではなく、アプリは取得した記録を自分の出力から除外できる。[4][6]

**freeism専用PDS・Solidサーバーの自作は、初期実装の必須条件にしない。**

検証をfreeismの登録APIと外部取り込み処理に入れれば、正式データとしての採用を制限できる。自前のPDS・Solidサーバーで保存前にも拒否したい場合は、同じ検証を全書き込み経路へ追加する。

ただし、自前サーバーでの保存前検証は、他のPDS・Podへ保存されたデータまで制御しない。複数の保存先と相互運用するPointsでは、取り込み時の検証も残す。相互運用のために「freeism専用PDSに置かれたデータだけが正しい」という条件にはしない。

本人・アカウントの認証では、AT ProtocolのDIDと正当な認可サーバーの対応、およびSolidのWebIDと正当なOIDC issuerの対応を検証する。[8][9] SolidのWebIDとPointsで用いるDIDを結び付ける具体的な方式は、別途定義する。

**段階導入では、データの識別・権限・証明を外部プロトコルから切り離しておく。**

Accountsで合意したv0.1／v0.2の分割をPointsへ展開する場合、v0.1では安定ID、評価グループの識別、投稿権限、Accounts AのVC受理ルール、重複防止、更新版・削除記録、選択データの変換を先に設計する。

v0.2では、Spaces・Solidへの接続、選択された非公開データの同期、アプリ別権限、手動取り込み、競合・未知項目・失効処理を追加する。この分割なら、外部プロトコルを追加しても、貢献度の帰属と権限判定の中核は置き換えずに済む。

Spacesはalphaでも対応を進める方針を維持する。ただし、公式の本番利用・機微情報投入に関する警告とは区別し、まず合成データで必要な拒否テストを行う。[4] 認可方式が必要な制限を保証できない保存先では、公開化や権限拡大で代替しない。

**詳細設計として残っている事項を、確定方針と分けて管理する。**

| 未決事項 | 定義・検証する内容 |
| --- | --- |
| 共通データ形式 | グループID、投稿者、対象SNS／DID、VC参照、評価値、版・削除の共通表現とSpaces／Solidへの対応 |
| グループ権限と登録元 | 正当なオーナー、委任・取消、実際の投稿主体を別Pointsも検証できる方式 |
| VC運用 | SNS識別子、発行形式、鍵更新、期限・失効、紐づけ変更、過去評価への反映ルール |
| 外部のアプリ別権限 | OAuth直接アクセス、包括権限、継承、既発行トークンを含め、未許可アプリ・未許可項目を本当に拒否できるか |
| Pointsの処理範囲 | グループとサービスの対応、貢献度の集計とポイント残高への変換・消費の関係 |

特に、貢献評価の相互運用と、複数サービスで利用可能な残高・決済・二重消費防止は同じ問題ではない。本議論で後者まで解決済みとは扱わない。

**最終的に目指すのは、「本人の紐づけを偽れず、投稿権限を偽れず、評価内容は各グループが自由に決められる、選択的・非公開のPoints相互運用」である。データの保存とアプリの選択は分散し、本人性はAccounts A、評価は各グループという信頼の境界を明示する。**
