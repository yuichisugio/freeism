# Points Web App v0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `points.freeism.app` を、ポイント付与・ポイント管理だけを担う独立した Cloudflare Workers アプリとして新規実装し、承認済み v0.2 仕様を空の D1 から再現可能にする。

**Architecture:** 親計画が用意する TanStack Start の静的SPA shell + 4固定route prerender と Workers Static Assets の上に、Hono の browser BFF／Public API／OAuth Resource API、Better Auth、Drizzle ORM、アプリ専用 D1 を配置する。経済状態は append-only ledger を正本とし、FIX、所有権、取引、予約を D1 の原子処理と冪等結果で収束させる。Markets との接続は Points 所有の OpenAPI と OAuth Bearer Token を通す。

**Tech Stack:** Node.js `24.18.0`、pnpm `10.33.3`、Vite Plus `0.2.4`、Vite `8.1.4`、TanStack Start `1.168.27`、React `19.2.7`、Hono `4.12.28`、`better-auth`／`@better-auth/drizzle-adapter`／Points専用`@better-auth/oauth-provider`／standalone CLI `auth`の各`1.7.0-rc.1`（開発・staging限定）、Drizzle ORM `0.45.2`、Drizzle Kit `0.31.10`、Cloudflare Workers／Static Assets／D1、Wrangler `4.108.0`、Vitest `4.1.10`／Workers pool `0.18.2`、`@playwright/test` `1.61.1`。

- 親計画のPoints shell Taskから受け取る package scripts は `dev`、`preview`、`check`、`test`、`test:worker`、`test:e2e`、`build`、`build:staging`、`build:production`、`build:assert`、`types:worker` である。`test:e2e`のscript、Playwright config、browser install方針は親shell Taskだけが所有し、本計画はE2E test内容だけを追加する。Task 1で`db:generate`と`db:migrate:local`、Cloudflare resource確定後の親Task 6A直前staging bootstrapで`db:migrate:staging`と`deploy:staging`を初回作成する。production migrate/deploy/smokeはTask 18と親Task 9が所有する。各 command は repository root から `pnpm --filter @freeism/points-web-app` に本計画記載の script 名と引数を続けて実行する。
- 仕様の正本は [Points v0.2](../docs/v0.2/index.ja.md)、[横断アーキテクチャ](../../../docs/web-app/v0.2/architecture.md)、[認証](../../../docs/web-app/v0.2/authentication.md)、[Points–Markets 契約](../../../docs/web-app/v0.2/points-markets-contract.md)、[レスポンス](../../../docs/web-app/v0.2/response-format.md)、[命名規則](../../../docs/web-app/v0.2/naming-convention.md)、[セキュリティ／デリバリー](../../../docs/web-app/v0.2/security-and-delivery.md)、[Decision Register](../../../docs/web-app/v0.2/decision-register.md) である。計画内の要約と正本が衝突した場合はDecision Register 20節に従い、後発の`採用`DEC、`一部上書き済み`DECの非上書き部分、正本本文の順に適用する。
- DEC-243のWeb再所有成功間隔、DEC-256のPoint Package Auction eligibility receipt、DEC-257のPackage文字／hash境界、DEC-258のCSV export上限、DEC-259の代用計算、DEC-260の自動分配、DEC-261のaccount close／reopenはすべて`採用`済みであり、本計画に記載した確定値をそのまま実装する。
- 後方互換、既存データ移行、旧 URL redirect、旧 Prisma schema の再現は行わない。Task、Group、一般 community member、Auction、bid、SSE、Upstash Redis、Next.js、Server Actions、Supabase、Vercel runtime を Points に持ち込まない（DEC-001〜DEC-009、DEC-027〜DEC-033、DEC-262）。
- Points と Markets は DB、Better Auth secret／schema、Cookie、domain model、環境 Secret を共有しない。共有可能なのは Points 所有の OpenAPI artifact とそこから生成した client だけである（DEC-016〜DEC-020、DEC-087〜DEC-097）。
- Static Assets、`/index.html` shell、`/terms|privacy|help|docs` prerender、custom fallback は親計画の責務とし、本計画から汎用 SPA fallback を追加しない。`/api/*` と `/.well-known/*` は Worker-first、存在しない asset／API へ HTML を返さない（DEC-153、DEC-154、DEC-235、DEC-236）。
- browser session は host-only の `Secure; HttpOnly; SameSite=Lax; Path=/` Cookie に限定する。認証済み response は `private, no-store`、mutation は同一 origin、JSON、Origin／Fetch Metadata、session、authorization、必要な `Idempotency-Key` を検査する。
- 利用者委任Access Tokenは`disableJwtPlugin: true`でopaque tokenに固定する。環境ごとにMarkets利用者用、M2M用、Settlement retry用Client IDを分け、Points Resource middlewareとMarketsは標準Resource Clientのconfidential remote introspectionを使う。credentialはWorker Secretだけに置いてbrowserへ出さない。利用者principalは利用者用Client＋pairwise `sub`あり＋利用者scopeだけ、M2M principalはM2M用Client＋利用者`sub`なし＋M2M scopeだけから導出し、標準responseへ独自`token_class`／`grant_type` claimを追加しない。JWTとしてdecode／JWKS検証せず、ID TokenをResource API Bearerとして受理しない（DEC-089、DEC-232、DEC-263）。
- Points の Social Provider は Google と GitHub の同一集合とし、`signIn.social` と `linkSocial` の provider allowlist を分岐させない。provider 別 sign-in 拒否 hook は作らない。email 一致による暗黙 link は禁止する（DEC-050、DEC-052、DEC-058〜DEC-060）。
- `trustedProviders`には同じGoogle＋GitHubの正本集合を使い、`disableImplicitLinking: true`を維持する。Social OAuth Tokenは`account.encryptOAuthTokens: true`とWorkers Secrets由来のBetter Auth標準versioned secretsで暗号化し、独自AES-GCM envelope／key ring／read時lazy rewrapを作らない（DEC-266）。
- Task 1はBetter Auth標準Accountの既存Account再利用までを扱う。永久`providerId + accountId -> Points userId`対応、app-owned table、複合一意制約、close後の再開はTask 9で完成させ、Task 9未完了ではTask 10以降とproduction releaseへ進まない（DEC-061、DEC-266）。
- 金額は scale `10_000` の D1 `INTEGER` と ASCII 十進文字列だけを使う。計算途中の `BigInt` は許可するが D1 bind 前と API 返却前に `Number.isSafeInteger` を検査し、`REAL` と浮動小数点で経済計算しない（DEC-107〜DEC-110）。
- CSV は UTF-8、最大 5 MiB、最大 1,000 非空行、server 再 parse、server draft なし、全件成功または 0 件とする（DEC-112〜DEC-119、DEC-225）。
- D1 migration は Drizzle Kit で sequence を生成し、`drizzle/` の生成 SQL を review してから commit する。schema source と生成 migration を同じ commit に入れ、`drizzle-kit push` を CI／staging／production で使わない。
- 各 task は記載順に実行する。先に失敗する test を追加し、指定 command の失敗理由を確認し、最小実装を加え、同じ test と task 指定の回帰 command を通してから commit する。別 task の機能や refactor を同じ commit に混ぜない。
- Workers integration test は毎 test で空 D1 に全 migration を適用する。外部 OAuth／fetch は fixture server か fetch stub を使い、実 credential と個人情報を repository に保存しない。
- 開発・stagingは`better-auth`、`@better-auth/drizzle-adapter`、Points専用`@better-auth/oauth-provider`、standalone CLI `auth`を各`1.7.0-rc.1`へ完全固定する。rootの`minimumReleaseAge: 4320`（72時間）を緩和せず、`minimumReleaseAgeExclude`等の例外を追加しない。exact packageがcooldown中ならversionやpolicyを変えず、72時間経過までTask 1のinstallを停止する。本番の4 package正式`1.7.0` exact bump、schema差分確認、両appの全認証回帰、production assertionは親計画のfinal release gateだけが所有し、本計画はRCを本番へ出さず、Task 1／2／14の回帰testを親gateへ引き渡す（DEC-085、DEC-086）。
- すべての success body は `{ data, meta? }`、error は RFC 9457 Problem Details と `SCREAMING_SNAKE_CASE` code を返す。stack、SQL、token、secret、内部 binding 名を返さない。
- production への deploy は親計画の main push pipeline だけが行う。本計画の各 task では local test／build までとし、Cloudflare resource の作成・staging／production deploy・旧サービス撤去は行わない。
